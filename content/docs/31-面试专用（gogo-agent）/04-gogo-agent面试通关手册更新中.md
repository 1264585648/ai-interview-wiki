# gogo-agent面试通关手册（更新中）

项目做了多智能体，拆分的核心判定标准是什么？

**先看上面的多智能体为什么要用**，然后再通过下面的条件，判断该如何拆，满足 2 个以上就应该拆：

**条件 1：需要独立的多轮推理循环**

最核心的判据。如果任务需要"收集信息 → 调用工具 → 看结果 → 再决策 → 再调工具"这样的循环，它就需要自己的 ReAct 循环。

**正例**：`ItineraryPlanAgent` 做行程规划，一次任务要搜多轮机票酒店、做比价、审核方案、发现问题再补搜，可能迭代 20-30 轮。**反例**：`IntentRecognitionAgent`（意图识别）虽然是"Agent"，但我们刻意没用 ReActAgent。因为意图识别是单轮 LLM 调用——输入一句话、输出一个 JSON，不需要工具也不需要多轮推理。套 ReActAgent 包装只会增加不必要的循环开销和 memory 开销。代码注释里专门写了这个决策。

**条件 2：需要独立的 System Prompt 和角色定位**

每个 Agent 有自己的"人格"。`ItineraryPlanAgent` 是行程规划专家，`BookingAgent` 是预订执行专家，`InfoAgent` 是信息查询专家。它们各自有独立的 system prompt 文件，定义了不同的行为边界和工作流。当两个任务的指令体系差异很大时，硬塞进同一个 Agent 会让 prompt 臃肿且互相干扰。

**条件 3：需要独立的工具集和 Hook 生命周期**

不同 Agent 的工具集和 Hook 几乎没有交集：

| Agent | 专属工具 | 专属 Hook |
| --- | --- | --- |
| ItineraryPlanAgent | 行程规划引擎、审核工具、方案 HTML | PlanAwareThinkingHook、SearchResultCaptureHook |
| BookingAgent | 预订写操作 | BookingPersistenceHook |
| InfoAgent | 3 个 RAG 知识库 | — |

如果两组能力挂载的工具集正交，或 Hook 的生命周期差异很大（比如预订落库只在 Booking 阶段需要），拆开更干净。

**条件 4：需要独立的记忆域和会话隔离**

每个 Agent 实例有独立的 memory 和 session。`BookingAgent` 的对话历史不会污染 `ItineraryPlanAgent` 的上下文，反之亦然。当两个任务需要维护各自独立的"记忆"时，就应该拆。

**条件 5：需要不同的模型和推理配置**

我们有三种模型：`stableModel`（轻量快速）、`strongModel`（强推理）、`strongModelWithThinking`（深度思考 + thinkingBudget）。不同 Agent 按需选用——路由决策用 strongModel，行程规划用 thinking 模型，意图识别用 stableModel。拆开后可以为每个 Agent 精细调优成本和效果。

什么情况下应该拆成独立 Agent，什么情况下更适合做成 Skill 或 Tool？

**Agent 是有大脑的决策者，Tool 是有手的执行者，Skill 是一份操作手册。**判断一个能力该做成什么，核心看三个问题：

1. 它需要"思考"吗？（多轮推理循环）
2. 它是确定性计算还是流程编排？
3. 它需要独立的人格/记忆/生命周期吗？

以我们项目为例，`ItineraryPlanAgent`（行程规划）配置了 `maxIters=30`，意味着一次行程规划最多迭代 30 轮：搜机票 → 搜酒店 → 比价分析 → 方案审核 → 发现问题 → 补搜修复 → 再生成方案。这种复杂度不可能塞进一个函数调用里。

*（其他的智能体，比如行程管理，他需要多种工具的调用，比如查询差旅信息，差旅的CRUD，审批的发起，以及差旅冲突的检测等，并且他需要记忆来做多轮对话，需要LLM来理解用户的自然语言，所以， 他也得是个Agent。*

*再比如信息查询智能体，因为他需要查询很多信息，比如天气、新闻、签证信息等等，并且需要多种工具的组合以及失败后的反思，并且在差旅政策查询时，需要agent能理解什么时候查政策，什么时候查用户信息，所以他也需要思考，所以他也得是个Agent）*

而工具，他的特点是**输入确定、输出确定、不需要 LLM 参与决策。** Tool 只做一件事：查数据库、做计算、调 API。比如我们的差旅单查询工具、行程规划的方案设计工具，因为他们都是基于确定的输入做确定的输出的。

但是其实也有例外，因为我们的项目中，子智能体对于主智能体来说，其实是Agent as Tool的方式交互的，子智能体对于主智能体来说也是通过工具的方式调用的。比如我们的审核智能体，其实我们就是为了编排一些确定性的审核、以及基于LLM的审核，而把一个智能体做成了工具，原因就是他的输入确定，输出的内容虽然不确定，但是执行的流程确定，输出的内容的方模板，或者说内容的基本格式是确定的。

Skill 是介于两者之间的独特抽象。它本质上是一份 `SKILL.md` 文件——一段结构化的提示词，包含领域知识、操作流程和约束规则。

**Skill 本身不是代码，不能被"调用"。** 它的正确使用方式是：Agent 通过 `SkillBox` 加载 SKILL.md → 阅读理解里面的指令 → 按照指令调用真正的 Tool 来完成任务。

我们项目中主要用到了两个skill ，其中有一个是帮我们做机酒、火车票查询和预订的第三方OTA提供的skill，它包含一整套旅行操作 SOP：怎么搜机票、怎么下单、怎么处理退改签、怎么格式化结果。这些"知识"写出来有几百行，但本身不执行任何代码——Agent 读完之后自己决策该跑哪些 shell 命令。

行程规划为什么用 Plan-and-Execute Agent，而其他模块用 ReAct Agent？

规则 → 向量 → LLM 兜底，整体介绍下这个方案？为什么这么做？

原来的方案中，每一轮对话都要串行跑三次 LLM——QueryRewriting（问题改写）→ IntentRecognition（意图识别）→ MasterAgent（路由），带来高延迟（秒级）和高成本。

但意图识别本质上是个**封闭集分类问题**（就 15 种意图，见 IntentCategory.java），大量用户输入是表达清晰、高度模板化的（“帮我查下机票”“差旅政策是什么”）。用大模型去算一个规则就能判定的分类，是资源浪费。

于是我设计了一个L0-L3的多层方案编排，命中即短路，尽量避免大模型调用。

```
用户消息
  │
  ├─ L0 结构启发：句中出现"然后/顺便/接着"等强连词且句长≥10 → 疑似多意图复合句
  │    → 直接跳过 L1/L2 交给 L3（因为 L1/L2 结构上只能产出单意图）
  │
  ├─ L1 规则匹配：单类命中 → 短路返回
  │    子句级多类命中且跨目标子智能体 → AMBIGUOUS，连 L2 一起跳过交给 L3
  │
  ├─ L2 向量检索：top-1 相似度 ≥ 0.75 且与 top-2 分差 ≥ 0.05（margin 校验）→ 短路返回
  │
  └─ L3 LLM 兜底：处理复杂表达、指代消解、多意图判定
```

- 规则：零成本、零延迟、判定可解释，但无法泛化——换个说法就失效；
- 向量：能捕捉语义相似（“我想飞过去”≈“查机票”），但存在阈值边界模糊、复合句 embedding 会同时贴近多个意图的问题；
- LLM：唯一能做多意图判断、指代消解、结合上下文消歧的，但最贵最慢。

顺序排列后，每层只接收上一层“搞不定”的流量：高频模板句在 L1 消化，口语化变体在 L2 消化，真正复杂的长尾才付 LLM 的代价。

L1和L2的意图识别，如何避免误判？

为了避免误判的发生，我们其实并不是命中了就返回的。

L1 规则保守，用负向词排除跨类干扰（如“报销政策”不命中报销意图而是政策查询），不确定就放行；

L2 的 margin 校验：top-1/top-2 分属不同意图且分差 &lt; 0.05 时，判定为“意图摇摆”，主动放行给 L3，避免复合句的另一半意图被“吞”掉；

L0 结构启发直接拦截多意图复合句。

误判的代价是路由错误（用户可感知的错误），漏判的代价只是多走一次慢路径——这个不对称性决定了所有守卫都往“保守放行”方向设计。

如果用户有多个意图，怎么办？L1、L2会不会识别错？

如何维护L1和L2的规则，如何确保他的准确性？

采用bad case监控+测试驱动+反哺的方式定期维护L1和L2：

```
线上日志/用户反馈发现 bad case
        │
        ▼
先写失败测试（红）── IntentRuleMatcherTest / SeedExamplesTest 加用例
        │
        ▼
最小化修改（绿）── 改 L1 规则 or 改 intent-seed.yml
        │
        ▼
全量跑测试 ── 四个测试类约 600 行护栏防止改 A 坏 B
        │
        ▼
上线观察 ── 看 [INTENT_ROUTER] 日志确认 case 修复且无新退化
```

尽量保证L1的稳定，遇到新的问题，优先考虑补充到L2中，如果L2中的规则命中率比较高的情况在，再考虑迁移到L1

独立时间消息为什么能提升 KV 缓存命中？

在 LLM 推理中，当多个请求的 prompt 共享相同的前缀 token 序列时，引擎（如 vLLM、TGI）可以直接复用已计算好的 KV 向量，跳过大量重复计算。

但是需要注意的是，**前缀缓存是从头开始逐 token 匹配的。 一旦某个位置的 token 发生变化，该位置之后的所有缓存全部失效。**

为了避免时间在系统提示词中导致缓存失效，我们可以将时间信息放到最后，或者是像我们项目一样，统一处理，即在system message之后统一加一条带当前时间的msg

开放性政策和个性化答案的判定标准是什么？

**核心判定标准：问题是否绑定用户身份**

我们通过提示词来做的判定：

- 问题特征如果是：“差旅制度里关于 X 是怎么规定的？”“差旅报销要走什么流程？”，走RAG通道
- 问题特征如果是：“我去 X 城市的住宿标准？”“我的差旅标准？”，走工具调用通道
- 问题同时命中两个通道时 → 优先通道 2（PolicyTools），以工具查到的精确结果为准
- 两个通道都无结果 → 统一返回“暂未收录该政策”，建议联系 HR
