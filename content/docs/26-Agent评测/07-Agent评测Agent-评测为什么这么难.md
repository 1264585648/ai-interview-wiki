# ✅Agent评测：Agent 评测为什么这么难？

为什么不能用传统评测？

先抛出一个问题：**Agent 评测到底难在哪，为什么以前那套测试方法用不了了？**

核心就在于：**Agent 的输出是开放的、非确定的，很难找到一个可以直接对比的“标准答案”。**

同一个问题，Agent 连续回答两次，可能措辞不同，甚至结论都可能存在差异。更麻烦的是，它最终交付的往往不是“选 A 还是 B”这样的固定选项，而是一份包含数据、分析和结论的自然语言报告。**输出不可预测、结果难以直接比较，这就是 Agent 评测最大的难点。**

对比一下 BIRD 就很直观。BIRD 虽然是在评测 Text-to-SQL 模型的能力，但它巧妙地找到了一个**确定性的评测锚点**：模型生成的 SQL 最终会落到数据库上执行。预测 SQL 和标准 SQL 不需要逐字比较，而是分别执行后，对比最终结果集是否一致。

也就是说，**SQL 本身虽然是模型生成的、具有随机性，但 SQL 的执行结果是确定的、可比较的。** BIRD 正是利用这个确定性的结果，把一个看似开放的生成任务，转化成了一个可以自动判定的结果对比问题。

但真正的 Agent 不一样，Agent 最终交付的是一份自然语言报告，没有一个天然存在的“执行结果集”可以直接拿来比较。报告里的数字是否正确、分析是否合理、有没有遗漏关键信息、有没有编造数据、结论是否有依据，这些问题都无法靠简单的字符串匹配或程序断言解决。

**传统的“标准答案 + 自动断言”评测方式，在这里就失效了。**那怎么办？通常有两条路：**人工评审，或者让大模型来评审。**

人工评审最直观，但问题也很明显：主观性强，不同评审人员对同一份报告可能给出不同判断；同时成本高、速度慢，当评测需要反复运行、对比多个 Agent 版本时，很难规模化。

因此，目前更适合 Agent 开放式输出评测的方案，是 **LLM-as-Judge**：让一个大模型充当“裁判”，按照预先定义好的评测标准，对 Agent 生成的报告进行评价和打分。

**所以，这一系列的 Agent 评测，我们也沿着这条思路展开：不再要求 Agent 给出一个能够直接断言的固定答案，而是建立一套评价标准，让 LLM Judge 从多个维度判断 Agent 的回答到底好不好。**

真正难在哪？

不过，**LLM-as-Judge 解决的只是“怎么判”的问题，并没有解决 Agent 评测本身的难题。**

Agent 和普通的 LLM 问答相比，最大的区别在于：它不是一次生成答案，而是一个**多轮、带工具调用的动态执行过程**。真正评测起来，主要难在三个地方。

ReAct 多轮交互

一次任务可能要跑十几轮甚至几十轮，每一轮都依赖前面的上下文。这就带来了一个问题：**上下文管理本身就可能出错。**

比如上下文压缩丢失了关键信息，或者因为长度限制截断了前面的事实，Agent 从某一轮开始就建立在错误的信息上。第一轮错一点，后面可能全部带偏，最后生成的答案看起来依然有模有样，但实际上根已经错了。

工具调用

Agent 区别于 LLM 的根本就在于 Agent 可以调用大量的工具，然而，工具调用本身也可能成为错误来源。

比如：

- 该调用的工具没有调用；
- 工具参数传错；
- 调用了错误的工具；
- 工具返回的数据本身有问题；
- 工具返回结果过大，导致上下文被污染甚至超限。

所以，**Agent 规划对了不代表最终结果一定对，只要工具链中间错一步，最终答案一样可能翻车。**

大模型随机性

Agent 区别于传统程序测试最关键的问题就是：**随机性。**

同一个问题、同一套 Prompt、同一个 Agent，连续运行多次，可能这次回答正确，下次却出现错误。

因此，**一次运行得到的结果，并不能完全代表 Agent 的真实能力。**

| **难点** | **具体表现** | **麻烦在哪** |
| --- | --- | --- |
| **ReAct 多轮交互** | **十几到几十轮，每轮依赖上文；压缩丢信息、截断丢事实** | **每一轮错一点，后面全带偏** |
| **工具调用** | **该调的没调、参数传错、返回错数据、结果过大塞爆上下文** | **规划对不代表结果对，工具链错一步就翻车** |
| **随机输出** | **同样输入，这次对下次错** | **一次跑通说明不了水平** |

这三个问题叠加之后，会带来两个更麻烦的后果：

**第一，错误会级联放大。**

前面任何一个环节出错，都可能影响后面的所有步骤，最终答案可能和正确结果差得很远，但中间每一步单独看又似乎都有道理。

**第二，错误很难定位。**

最终答案错了，并不能直接说明是模型推理错了、工具调用错了、上下文管理错了，还是其他环节出了问题。对于 Agent 来说，最终的答案错误只是表象，真正的问题可能隐藏在几十轮执行过程中的某一步。

小结

传统评测的前提是“输出可预测、可对比”。BIRD 评的是 SQL 的执行结果集，借到了确定性的锚点，基本还在传统评测范畴；Agent 交付的是自然语言报告，输出开放、随机，没法直接断言，传统方法在这里失效。**出路是 LLM-as-Judge：让大模型当裁判，人工评审主观、贵、慢，撑不起规模化。**

但 LLM-as-Judge 只解决了“怎么判”，Agent 评测本身的难还在三处：**多轮上下文会出错、工具调用会出错、输出天然随机。** 三者叠加，错误会级联放大，而且藏在几十轮执行过程里，很难定位。

这三个难点，就是后面评测体系每一处设计的由来。
