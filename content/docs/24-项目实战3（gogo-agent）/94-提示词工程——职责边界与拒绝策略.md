# ✅提示词工程——职责边界与拒绝策略

提示词很多时候都是在告诉LLM可以做什么，怎么做。，但是，不能做什么也非常重要。这就涉及到职责边界和拒绝策略的提示词工程优化了。

**职责边界（能做什么）**：每个 Agent 被限定只处理自己那一档业务。规划的不下单，下单的不规划，问信息的不改单。它回答的是「这件事该不该由我来做」。

**拒绝策略（在什么条件下不做）**：即使一件事落在我职责内，也存在「前置条件没满足就必须停手」的红线。比如预订本是 BookingAgent 的职责，但「差旅单还没审批通过」时它必须拒绝下单。它回答的是「这件事现在能不能做」。

为什么需要：单 Agent 全能会「越权」和「幻觉」

假设整个差旅系统只有一个「全能 Agent」，把提交审批、规划行程、比价预订、报销全塞进一个 Toolkit，会立刻踩三个坑：

第一，**越权拍板**。用户说「帮我把这个出差申请通过了」，一个持有「审批通过」工具的 Agent 很可能真的去调它——可审批权本该属于管理员，不属于发起人，更不属于替发起人说话的 AI。

第二，**阶段错位**。用户刚说完「帮我规划去杭州的行程」，Agent 一高兴把机票酒店全订了。可此时差旅单可能还没审批通过，订了就是既成事实、要走退改。

第三，**幻觉编造**。当某个查询工具返回空、或用户没给全参数时，一个「不甘心」的 Agent 会自己脑补一个航班号、编一段差旅政策糊弄过去。

gogo-agent 的解法是把系统拆成 MasterAgent（总控路由）+ 若干专业子 Agent（ItineraryManage / ItineraryPlan / Info / Booking / Reimbursement），每个 Agent 各自持一套**最小必要工具**，并在提示词里写清「我不做什么、什么条件下拒绝」。下面逐层看它是怎么写、怎么用代码兜底的。

总控不越权，只路由 + 透传（MasterAgent）

MasterAgent 是唯一总入口，但它的 Toolkit 出人意料地「空」——它只有一个 ask_user（人机交互）和四个「子 Agent 作为工具」，**没有任何一个业务写操作工具**：

```text
// agent/MasterAgent.java:79-118（节选）
Toolkit toolkit = new Toolkit();
toolkit.registration().tool(new UserInteractionTools()).apply();   // 只有 ask_user

toolkit.registration()
    .subAgent(() -> context.getBean("itineraryManageAgent", ReActAgent.class),
        SubAgentConfig.builder().toolName("itinerary_manage_agent")...build())
    .apply();
// 同理注册 itinerary_plan_agent / info_agent / booking_agent
```

对应提示词把「不越权」写成了明文红线：

```text
<!-- prompts/master-agent-system.md:65 -->
8**不越权**：你不直接操作预订、提交审批等变更行为，必须通过对应子智能体完成。
```

更关键的是 MasterAgent 对子 Agent 返回结果的处理规则——它被明确禁止「用自己的话覆盖子 Agent 的方案」：

```text
<!-- prompts/master-agent-system.md:60-63 -->
- 优先将子智能体的回复内容直接透传给用户，禁止用自己生成的新回复覆盖或替代。
- 若子智能体返回中包含待用户确认的内容（如审批单摘要、行程方案…），必须原样保留全部关键信息与确认问句。
- 若子智能体要求用户确认，必须原样保留确认请求，不得擅自替用户决定。
```

条件式硬拒绝（BookingAgent ）

BookingAgent 是唯一能真正「下单」的 Agent，但它的下单被一道**强制审批门禁**卡住。提示词把它写成不可绕过的红线：

```text
<!-- prompts/booking-agent-system.md:8-10 -->
2. 审批检查（强制，不可跳过）：执行预订前，必须调用
   query_travel_order(status="APPROVED") 确认存在已审批通过的差旅单：
   - 若存在 APPROVED 订单：可执行预订。
   - 若不存在 APPROVED 订单：直接拒绝预订，告知用户"差旅单尚未通过审批，
     无法执行预订。请先提交差旅申请并等待审批通过后再预订。"，
     不得以任何理由绕过此检查。
```

反幻觉边界（缺参数追问、召回为空不编造）

这是「拒绝策略」里最日常的一类：宁可停下问，也不许编。InfoAgent 的提示词把「禁止行为」列成清单：

```text
<!-- prompts/info-agent-system.md（要点） -->
- 不修改/提交/取消差旅单（不属于我的职责，移交）
- 不代替用户做决策
- 缺少关键参数时直接向用户提问，不得自行假设
- 检索/召回为空时如实告知，禁止编造政策或景点信息
```

ItineraryPlanAgent 同样写死了「禁编造方案」；意图识别 Agent 在低置信度时不硬猜，而是回退到 masterAgent 让人来兜（intent-recognition-agent-system.md:75-77）。

输出边界（不泄露内部名 + 不写敏感记忆）

最后一类约束不关乎业务动作，而关乎「对用户说话的姿态」。几乎每个提示词末尾都有一条**禁词兜底**，禁止把 snake_case 工具名、子 Agent Bean 名、内部字段名、文件路径暴露给用户：

```text
<!-- prompts/master-agent-system.md:139（节选） -->
禁止向用户暴露内部名称（兜底）：… 一律不得出现工具函数名、子智能体名、
内部字段名与文件路径（如 query_destination_news、plan_itinerary、
itinerary_plan_agent、primary_intent 等 snake_case 名称）。若子智能体的回复中
遗漏了此类名称，在透传前将其改写为中文自然语（如"目的地新闻查询""行程规划工具"）…
```

配套还有长期记忆的写入边界：master-agent-system.md:131「不要记录敏感信息（如身份证号、密码、具体金额），只记录与差旅选择相关的偏好」。这条同样是纯提示词约束。
