# ✅上下文工程——工具返回用摘要代替完整内容

我们的项目中，有一个工具的返回非常用重要，就是planItinerary，正常情况下他会把完整的规划出来的方案都返回给LLM，但是我们返回之前，调了一把buildSummary 方法，他的作用是 plan_itinerary 工具返回给 LLM 的轻量摘要，它的核心设计意图是：不把完整结果 JSON 返回给 LLM，而是只返回一个精简的统计摘要。

```
{
  "ok": true,
  "redis_key": "itinerary_plan:user123",
  "combo_count": 48,
  "proposal_count": 3,
  "tags": { "综合最佳": 82.5, "价格最低": 71.3, "时间最短": 79.0 }
}
```

**为什么要这么做？**

**1. 节省 Token / 避免信息过载**

完整的结果 JSON（存在 Redis 里的那个）非常大——包含每个 proposal 的去程/酒店/返程详情、各项评分、政策违规信息、偏好理由等。如果把所有这些直接作为 Tool 返回值塞回 LLM 上下文，会消耗大量 token，而且 LLM 在一堆结构化数据中容易"迷路"。

摘要只告诉 LLM："规划完成了，有 N 个组合，选了 M 个代表方案，各自标签和综合分是多少"——这些足够 LLM 生成一段自然语言回复给用户了。

**2. 数据与展示分离**

完整的方案数据已经通过 itineraryPlanStore.save(userId, resultJson) 存入了 Redis。后续前端展示（如行程卡片渲染）或用户选定方案时，通过 redis_key 从 Redis 读取完整数据即可，不需要经过 LLM 中转。

这就形成了一个清晰的分工：

LLM 拿到摘要 → 用来组织自然语言回复（"为您找到了 3 个方案，综合最佳得分 82.5…"）

前端/下游服务拿完整数据 → 通过 Redis key 直接读取，用于 UI 渲染

**3. tags 字段让 LLM 快速定位亮点**

tags 把每个代表方案的标签（综合最佳/时间最短/价格最低/最符合偏好）和对应的 overall 分数提取出来，LLM 可以很方便地在回复中突出这些亮点，而不需要从嵌套的 JSON 结构里自己解析。

总结一句话：buildSummary 是一种典型的 "Tool 返回精简摘要 + 完整数据旁路存储" 的设计模式，目的是控制 LLM 上下文大小、分离数据流和展示流，同时给 LLM 提供足够的信息来生成有意义的回复。
