# ✅提示词工程——结构化输出约束

在一个多 Agent 系统中，LLM 的输出不只是给用户看——它经常是**下游程序的输入**。gogo-agent 的意图识别结果直接被 Java 代码解析成路由指令、问题推荐的 JSON 数组会被前端渲染成气泡按钮、对话标题会被存进数据库当索引。

只要有一次 LLM 输出格式跑偏（多输出一句话、少一个引号、把 true 写成 "true"），整个后端就崩了。所以结构化输出约束不是"锦上添花"，而是 Agent 系统的**生命线**——它决定了 LLM 能否成为工程系统中可靠的组件。

翻遍 gogo-agent 的 11 个 prompt，结构化输出的目标可以归纳为三种形态，每种对应不同的约束强度：

```text
形态一：严格 JSON（机器可读，零容错）
   ↓  用于 Agent-to-Agent、Agent-to-Backend 数据流
   
形态二：模板化 Markdown（人机友好，结构可控）
   ↓  用于面向用户的富文本呈现
   
形态三：短文本片段（最简约束，语义为准）
   ↓  用于对话标题、单值输出等场景
```

| Agent | 输出形态 | 消费者 | 出错代价 |
| --- | --- | --- | --- |
| IntentRecognitionAgent | 严格 JSON | Java 反序列化 → 路由 | 系统崩溃 |
| QueryRewritingAgent | 严格 JSON | 上游 Agent 消费 | 意图丢失 |
| QuestionRecommendationAgent | 严格 JSON | 前端渲染气泡 | 按钮消失 |
| ItineraryPlanAgent | 模板化 Markdown/html | 用户阅读 | 体验下降 |
| ~~ItineraryReviewAgent~~ | 模板化 Markdown | Plan Agent 消费 | 审核失效 |
| ConversationTitleAgent | 短文本片段 | 存数据库 | 标题异常 |

严格 JSON 输出

严格 JSON 是最难写好的输出约束。gogo-agent 用了六种叠加手法来保证 LLM 稳定产出可解析的 JSON。

开门见山声明"只输出 JSON"

IntentRecognitionAgent 和 QueryRewritingAgent 的输出章节第一句话都是：

```text
必须只输出以下 JSON 格式，
禁止附加任何自然语言解释，
禁止调用任何工具：
```

这句话虽然简单，但包含三个关键要素：

1. **必须**（强制语气，不是"请")
2. **只**输出（排除任何附加内容）
3. **禁止**附加解释 + **禁止**调用工具（明确堵住 LLM 的两大越权本能）

反面案例：

```text
❌ "请返回 JSON 格式"          （太软，可能会附带"好的，这是JSON："）
❌ "输出 JSON 数据"            （没说不能带解释）
❌ "以 JSON 方式回复"          （"方式"暗示可能有变体）
```

给出完整可复制的 JSON 模板

```text
{
  "intents": [
    {
      "intent": "意图类别",
      "target_agent": "目标子智能体 bean 名（camelCase）",
      "confidence": "high|medium|low",
      "reason": "简要分类理由"
    }
  ],
  "primary_intent": "最主要意图类别",
  "multi_intent": true,
  "overall_reason": "整体分类理由，特别说明为何存在多意图"
}
```

关键技巧：

- **占位符本身即文档**："意图类别"、"目标子智能体 bean 名（camelCase）" 直接暗示了字段应该填什么
- **枚举值内联**："confidence": "high|medium|low" 用管道符列举可选值
- **样例默认值**："multi_intent": true 用 true 而非 false 提示这是布尔类型

紧跟字段说明表

模板之后必须紧跟字段说明：

```text
字段说明：
- `intents`：识别出的意图列表。单意图时只有一项，multi_intent 为 false。
- `target_agent`：必须是**目标子智能体在 Spring 容器中的 bean 名（camelCase）**...
  系统会直接通过 context.getBean(target_agent, ReActAgent.class) 查找并调用，
  命名必须严格匹配。
- `primary_intent`：当前最核心或最紧迫的意图。
- `multi_intent`：是否包含多个意图。
- `overall_reason`：整体判断理由...
```

关键技巧：

- **每个字段都要有说明**，即使含义看似显而易见
- **说明"为什么"**：告诉 LLM 系统会怎么消费这个字段（如 context.getBean(...)），让它理解格式的重要性
- **描述约束条件**：如"必须严格匹配"、"multi_intent 为 false 时" 等

用示例对齐输出格式

IntentRecognitionAgent 的 prompt 末尾有两个完整示例：

````text
### 示例 1：单意图 - 差旅申请

Rewritten question: `我要申请下周从北京去杭州出差，拜访阿里巴巴。`

Output:
```json
&#123;
  "intents": [
    &#123;
      "intent": "travel_application",
      "target_agent": "itineraryManageAgent",
      "confidence": "high",
      "reason": "用户明确提出出差申请，包含目的地和事由。"
    &#125;
  ],
  "primary_intent": "travel_application",
  "multi_intent": false,
  "overall_reason": "单一差旅申请意图。"
&#125;
````

用外部规则约束枚举值

对于枚举字段（如 `intent`、`target_agent`），单靠 `"high|medium|low"` 这种内联注释不够，必须提供完整的枚举表：

```text
| 意图类别 | 说明 | target_agent（camelCase） | 典型触发词/句式 |
|---|---|---|---|
| travel_application | 用户要提交新的差旅申请 | itineraryManageAgent | "我要出差""申请去xx" |
| travel_cancel | 用户要取消出差申请 | itineraryManageAgent | "取消出差""不去了" |
...16 个类别完整枚举
```

这张表的价值在于：

1. **穷举所有合法值**（LLM 不会创造新的枚举值）
2. **绑定语义**（每个枚举值配"说明"）
3. **提供触发词**（LLM 从用户输入到枚举值的映射有依据）
4. **多字段联动**（intent → target_agent 的映射关系一目了然）

模板化 Markdown 输出的约束设计

模板化 Markdown 比 JSON 更灵活，但也更容易跑偏。gogo-agent 用了几种手法来控制。

完整可复制的 Markdown 模板

ItineraryPlanAgent 的最终输出模板（后面我们把它挪到了skill中）：

```text
## 🗂️ 差旅行程方案（上海 → 杭州，2026-07-16 去 / 2026-07-18 返）

### 🏆 推荐方案 · 综合最佳
> **为什么是它**：在通过审核的方案里综合分最高（85）...

| 环节 | 详情 | 费用 |
|------|------|------|
| 🛫 去程 | 东航 MU5678，上海虹桥 07:30 → 杭州萧山 09:45，经济舱 | ¥620 |
| 🛬 返程 | 东航 MU5679，杭州萧山 20:10 → 上海虹桥 22:20，经济舱 | ¥620 |
| 🏨 酒店 | 全季酒店（西湖店），大床房，2 晚，¥413/晚 | ¥826 |
| **合计** | **行程耗时 4h05m** ｜ **评分** 时间80/价格90/... | **¥1313** |

### 📋 方案对比（需要挑选时看这里）
| 方案 | 标签 | 去程交通 | 返程交通 | 酒店(房型) | 总耗时 | 总价 | 评分 | 审核 |
| 方案1 ✅推荐 | ... |
...
```

Markdown 模板的关键设计：

- **具体数值/示例填充**（不留 xxx 占位符，LLM 更容易照抄结构）
- **视觉符号锁定**（🏆/🛫/🏨/📋/🔍 等 emoji 出现的位置固定）
- **表格列结构预设**（列名和列顺序不给 LLM 自由发挥空间）

结构与顺序强制

```text
- **结构与顺序（倒金字塔，必守）**：
  严格按「🏆 推荐方案 → 📋 方案对比 → 🔍 方案明细 
   → 🧭 Agent 为你做了什么 → 🧭 下一步」输出。
  推荐方案置顶（用户 80% 只看这里就够），
  审核把关紧随其后、置于明细之前，
  评估足迹放在最末。
```

这段约束包含三层信息：

1. **必守的顺序**（用箭头明确排列）
2. **顺序背后的理由**（"用户 80% 只看这里")
3. **各区块的相对位置**（"紧随其后"、"置于X之前"、"放在最末"）

告诉 LLM "为什么这么排" 比单纯 "按X排" 更能保证遵守。

区块级细粒度规则

对每个 Markdown 区块单独定规则：

```text
- **推荐方案（置顶必填）**：
  先用一句话 > 引用块说明为什么推荐它；
  随后**以 Markdown 表格呈现**（列：环节 / 详情 / 费用；
  行：🛫 去程、🛬 返程、🏨 酒店，末尾加 **合计** 行）。
  去程/返程详情含航班号/车次号、站点、出发/到达时间、舱位/席别，
  费用列填票价...

- **审核把关（引用块，显眼但不喧宾夺主）**：
  用 > 引用块 + ✅/⚠️ 图标，
  简述推荐方案审核结论 + 全部方案 summary...
  控制在 2–3 行，不得盖过推荐方案。

- **方案对比表**：
  每行含 标签、去程/返程交通（航班号/车次号 + 出发→到达时间）、
  酒店(房型)、**总耗时**、**总价**、五维评分、审核评级；
  推荐方案所在行标注 ✅推荐。
```

对每个区块声明：

- **格式载体**（引用块 / 表格 / 列表）
- **必填元素**（哪些字段一定要有）
- **长度约束**（"控制在 2-3 行")
- **视觉标记**（✅推荐 / ⚠️ 图标）

反编造的溯源约束

Markdown 输出的最大风险是 LLM 编造数据。ItineraryPlanAgent 有一段极其严厉的约束：

```text
- **禁止编造方案字段（重要）**：
  初稿/修复版/最终推荐里的航班号/车次号、承运人、
  出发/到达时间、舱位/席别、票价、酒店名、房型、晚数、
  每晚价、总价、总耗时、各维度评分，
  **必须逐字取自真实数据源**——
  你传入 plan_itinerary 的 candidates 对应条目、
  plan_itinerary 的返回，以及 itinerary_review_agent 的审核报告；
  不得自行编造或改写任何数值，
  数据源中不存在的字段一律留空不写，不得脑补。
```

这段约束的技巧：

1. **枚举所有易编造字段**（航班号/车次号/时间/价格...）
2. **明确合法来源**（三个具体的数据源）
3. **明确失败兜底**（"数据源中不存在的字段一律留空不写"）

对 Markdown 输出而言，"数据从哪来"比"格式怎么写"更重要——格式错了容易看出来，编造的数据可能骗过所有人。

区分事实与主观

```text
- **严禁编造用户偏好（重要）**：
  只有当 preferences 确系来自 retrieve_from_memory 且非空、
  且 planner 返回的 preference_basis 明确列出了命中项时，
  才可以在文案中描述"方案匹配了您的偏好"...
  
  若 preferences 为空字符串 ""（无长期记忆偏好），
  或 preference_basis 为"无偏好设置，使用中性分"，
  则**绝对禁止**声称方案匹配了航司、早班机、直飞、可退改、
  酒店品牌等任何用户未表达的偏好...
```

这种约束区分了"事实字段"（航班号=数据源）和"主观声称"（偏好匹配=需要 preference_basis 支撑），要求 LLM 对不同类型的输出承担不同强度的举证义务。

短文本片段的极简约束

ConversationTitleAgent 是短文本输出的典型案例，它的约束反而是最难写的——因为可以约束的地方少，每一条都必须精准。

```text
## 输出要求
1. 标题长度不超过 24 个字符（含标点）。
2. 直接输出标题文本，不要加引号、不要加序号、不要使用 Markdown。
3. 不要输出任何解释、不要输出 JSON。
4. **标题中禁止包含内部名称**...
5. 标题应准确概括用户当前意图，例如：
   - 出差申请 → "北京出差申请"
   - 行程规划 → "杭州行程规划"
   - 查机票 → "查询北京到杭州航班"
```

关键约束设计：

1. **量化长度**（24 字符含标点）—— LLM 只有量化才能自控
2. **穷举装饰禁忌**（引号/序号/Markdown/解释/JSON）—— 因为 LLM 天然想加装饰
3. **提供 few-shot 映射**（意图→标题的输入输出对）—— 短输出场景 Few-shot 比规则更有效

对比一下模糊约束：

```text
❌ "生成一个简洁的对话标题"        （多长算简洁？）
❌ "标题应该反映用户意图"          （怎么反映？）
❌ "不要太长"                     （多长算长？）
```

短输出场景，**数字约束 + 禁忌枚举 + 示例映射**是黄金三件套。

结构化输出的四层保护网

综合 gogo-agent 的实践，一个健壮的结构化输出约束应该有四层保护网：

```text
第一层：格式声明（"必须只输出 JSON"）
   ↓
第二层：模板样板（完整可复制的示例）
   ↓
第三层：字段说明（每个字段的语义、类型、约束）
   ↓
第四层：Few-shot 示例（2-3 个不同场景的完整示例）
```

四层保护网的作用是**逐层降低 LLM 出错概率**：

- 第一层约束"要不要输出格式"
- 第二层约束"输出什么样的格式"
- 第三层约束"每个字段应该怎么填"
- 第四层通过示例把前三层内化为 LLM 的模式识别

只有一层不够——比如只有第二层模板，LLM 可能会加解释；只有第三层字段说明，LLM 可能猜错字段类型。四层叠加才能达到生产可用的稳定性。

结构化输出的常见陷阱

从 gogo-agent 的严谨约束反向推导，可以总结出容易踩坑的地方：

陷阱 1：格式说了没模板

`❌ "输出 JSON，包含 name/age/city 三个字段" ✅ 提供完整可复制的 JSON 模板`

LLM 拼装 JSON 时容易漏引号、漏逗号，给完整模板它就照抄。

陷阱 2：模板有省略号

`❌ {"users": [{"name": "张三"}, {...}, ...]} ✅ {"users": [{"name": "张三"}, {"name": "李四"}]}`

任何 ... 都会让 LLM 以为可以自由发挥。

陷阱 3：多个 code block 混淆

有时 prompt 里会同时出现 "输入示例的 JSON" 和 "输出格式的 JSON"，LLM 可能搞混。gogo-agent 用了明确的段落标题区分：

```text
## 输入
- `rewritten_question`：...

## 输出格式
必须只输出以下 JSON 格式...
```

陷阱 4：字段说明写在模板里

`❌ {"name": "用户的姓名"} ✅ 模板里写 "name": "张三"，说明写在下方"字段说明"表格里`

把说明放在字段值里，LLM 可能真的输出 "name": "用户的姓名" 这种字面值。

陷阱 5：忘记禁止 code block 包裹

问题推荐 Agent 的一个细节：

```text
不要解释、不要道歉、
**不要输出 markdown 代码块标记**，
只输出 JSON
```

LLM 天然习惯把 JSON 包在 ```json 里，这在纯 API 消费场景会导致解析失败。必须显式禁止。

陷阱 6：多语言混用不一致

`❌ 字段名英文（"user_name"）+ 字段值有时中文有时英文 ✅ 全部字段名英文，明确规定哪些字段填中文哪些填英文`

gogo-agent 的 target_agent 字段严格要求 camelCase 英文（itineraryManageAgent），而 reason 字段严格要求中文自然语——每个字段的语言归属清晰不混淆。

写好结构化输出约束的检查清单

从 gogo-agent 的最佳实践中提炼出的清单：

**格式声明**

- 是否用"必须""只""禁止"等强制语气？
- 是否明确禁止附加解释、闲聊、道歉？
- 是否明确禁止调用工具（如果不需要）？
- 是否明确禁止 markdown 代码块包裹（如果输出纯 JSON）？

**模板设计**

- 是否给出完整、无省略号的模板？
- 模板中的占位符是否本身有语义？
- 枚举值是否用 a|b|c 内联标注？
- 是否用真实示例值而非 xxx？

**字段说明**

- 每个字段是否有独立说明？
- 是否说明字段的数据类型？
- 是否说明字段的合法值/取值范围？
- 是否说明字段会被下游怎么消费？

**示例覆盖**

- 是否至少 2 个 few-shot 示例？
- 示例是否覆盖不同场景（单意图 + 多意图、相关 + 不相关等）？
- 每个示例是否完整（输入 + 完整输出）？

**语言与命名**

- 哪些字段用英文？哪些字段用中文？
- 是否禁止在描述字段中出现英文技术标识？
- 枚举值的大小写规则是否明确？

**长度与格式细节**

- 短文本输出是否有字符数上限？
- Markdown 输出是否有区块顺序约束？
- 是否禁止某些装饰（引号、序号等）？

一个约束能通过这份清单，基本能达到生产级别的稳定性。
