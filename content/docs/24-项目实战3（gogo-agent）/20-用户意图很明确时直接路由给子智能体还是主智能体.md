# ✅用户意图很明确时，直接路由给子智能体还是主智能体？

我们之前的方案中，如果**"意图明确"**：

1. **单意图**（multi_intent = false 且 intents 恰好 1 项）；
2. **高置信**（该意图 confidence = high）；
3. **目标子智能体在"可直跳白名单"里**（当前白名单只有 infoAgent）。

那么我们就会直接调到这个Agent做执行。

但是后来这个方案被我**废弃掉了**。讲讲为啥：

在我们的流程中，有以下几种情况：

| 场景 | 子智能体 Session 有历史吗 | 上下文丢失吗 |
| --- | --- | --- |
| 首次对话 → L1/L2 命中 → 直跳 | 无 | 不丢（没有历史可丢） |
| 跟同一子智能体续聊 → L1/L2 命中 → 直跳 | 有 | 不丢（自身 Session 有） |
| 上一轮是别的 Agent → L1/L2 命中 → 直跳 | 无 | 丢（不知道之前聊了啥） |

第三种情况，比如我前面在和行程管理智能体对话，我问他我周末去哪里出差，行程管理智能体查询到我要去上海出差，我问他那里天气怎么样。

因为这一轮问题命中了天气查询的L1意图识别规则，直接路由给信息查询智能体，但是信息查询智能体不知道我们前面聊了啥，所以他根本不知道我问的是啥：

![](assets/1e81163f6164.png)

这就是我们前面的方案存在的问题。

那如果要解决这个问题，有三个方案：

- **方案一：快路径命中时，加载 chat_message 作为子智能体的系统上下文**
- 跟问题改写智能体同样的思路，把最近 N 条 chat_message 历史格式化成一条 SYSTEM 消息拼到子智能体输入前面。这样子智能体直接获得跨 Agent 上下文。
- **方案二：条件改写——有历史时即使 L1/L2 命中也走改写**
- L1/L2 命中后先查一下 chat_message 有没有历史记录，有历史就降级走改写流程（改写后的问题自包含），没历史（首次对话）才直跳。最安全，但首次之后的每次 L1/L2 命中都多一次改写 LLM 调用。
- **方案三：仅首次交互时注入历史**
- 检查子智能体的 Session key 是否存在，不存在（首次与该 Agent 交互）才注入 chat_message 历史，已存在就依赖自身 Session。精准注入，避免 Session 污染，但实现稍复杂。

其实，上面三个方案，我最开始考虑过第一个方案。但是这个方案相比不做直跳，干脆让MasterAgent做路由器来说，其实并没有带来非常大的优势。

| 维度 | 方案一（直跳 + 注入历史） | 不做直跳（走 MasterAgent） |
| --- | --- | --- |
| LLM调用 | 1 次（子智能体） | 2 次（MasterAgent + 子智能体） |
| 延迟 | 快 | 慢 1-3s（MasterAgent 推理） |
| 上下文来源 | chat_message 注入 | MasterAgent 自身 Session |
| 路由决策 | L1/L2 规则已确定意图 | MasterAgent 再推理一次（结果大概率一样） |
| token消耗 | 少 | 多（MasterAgent的历史msgs） |
| 是否会丢失信息 | 会 | 不会 |

也就是说，相比较之下，方案一这种直跳 + 注入历史的方案，会省一些token，但是因为他是靠读取最近N条chat_message来组装对话的，存在信息可能会丢失的可能。

所以说，两个方案，一个是优先省 token（方案一），一个是优先信息完整（不做直跳）。最终我的选择是先不做直跳了，优先考虑信息完整性吧。

![](assets/edb81175f545.png)

至于token，我们想办法从其他的地方省出来。

**但是！这个**~~**直跳**~~**的方案也不是完全不能用的，在我之前做过的项目中， 就有这种直跳的场景，有些Agent他就是比较独立，完全不需要依赖历史信息，或者是历史信息可以通过其他方式获得，比如共享对象等方式的话，也是可以考虑用的。**
