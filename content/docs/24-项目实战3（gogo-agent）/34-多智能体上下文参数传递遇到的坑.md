# ✅多智能体上下文参数传递遇到的坑

工具方法的第一个形参不带 `@ToolParam`，由框架的 `ToolExecutionContext` 按类型注入，对 LLM 完全透明：

```java

@Tool(name = "query_travel_order", description = "...")
public String queryTravelOrder(
        AgentSessionContext sessionCtx,          // ← 框架注入，不暴露给 LLM
        @ToolParam(name = "order_id", ...) String orderId,
        ...) {
    String userId = sessionCtx.getUserId();      // ← 这里 NPE
```

我们在构造子智能体的时候，也需要传入ToolExecutionContext，但是，这个子智能体subAgent如何构造并注册为主智能体的tool，也是有讲究的。这里有两种注册子 Agent 的写法，lambda 体一模一样，但只有第一种能让 `sessionCtx` 有值。

写法 1

```java
toolkit.registration()
        .subAgent((SubAgentProvider<ReActAgent>) () -> context.getBean("itineraryManageAgent", ReActAgent.class), config)
        .apply();
```

**写法 2（正确，当前实现）**

```java
Supplier<ReActAgent> manageAgentProvider = AgentSessionContextHolder.bind(
        () -> context.getBean("itineraryManageAgent", ReActAgent.class));
toolkit.registration()
        .subAgent((SubAgentProvider<ReActAgent>) manageAgentProvider::get, config)
        .apply();
```

最开始我用的是写法1，有问题。

写法1的问题复现

在 MasterAgent.java这行：

```
toolkit.registration()
        .subAgent((SubAgentProvider<ReActAgent>) () -> context.getBean("itineraryManageAgent", ReActAgent.class), ...)
        .apply();
```

subAgent 的第一个参数是 SubAgentProvider，一个函数接口。你现在只是 new 了一个对象塞进去，getBean 这句还没执行。

MasterAgent 跑起来，LLM 决定调用 itinerary_manage_agent 工具。AgentScope 会从工具表里取出这个对象，调它的 provide()，也就是执行你 lambda 里的 context.getBean("itineraryManageAgent", ReActAgent.class)。

**重点：这个执行发生在另一个线程 boundedElastic-1 上，不是 MasterAgent.build() 时的那个线程。**

又因为itineraryManageAgent 是 @Scope("prototype")，所以 getBean 不是拿缓存，而是现在、在 boundedElastic-1 这个线程上，跑一遍 build() 方法：

```
.toolExecutionContext(createToolCtx())
```

createToolCtx() 干了什么：

```
public static ToolExecutionContext createToolCtx() {
    AgentSessionContext sessionCtx = AgentSessionContextHolder.get();  // ← 读当前线程的 ThreadLocal
    if (sessionCtx == null) {
        logger.warn("[AGENT] 构建 Agent 时当前线程（{}）未携带 AgentSessionContext，"
                    + "工具形参 sessionCtx 将为 null，请检查上下文投递链路", Thread.currentThread().getName());
        return ToolExecutionContext.empty();   // ← 返回空上下文
    }
    return ToolExecutionContext.builder().register(sessionCtx).build();
}
```

当前线程是 boundedElastic-1，这个线程的 AgentSessionContextHolder 是空的，所以 sessionCtx == null，返回 ToolExecutionContext.empty()。

ToolExecutionContext.empty() 里面没有任何 AgentSessionContext 对象。框架给工具方法注入参数时，按类型从 ToolExecutionContext 里找 AgentSessionContext，找不到，就给 queryTravelOrder 的 sessionCtx 形参注入 null。

TravelOrderReadTools.java在执行的时候，就抛出NPE了。

**写法2 为什么不会？**

写法2多了 `AgentSessionContextHolder.bind(...)` 。

```text
Supplier<ReActAgent> planAgentProvider = AgentSessionContextHolder.bind(
                () -> context.getBean("itineraryPlanAgent", ReActAgent.class));
        toolkit.registration()
                .subAgent((SubAgentProvider<ReActAgent>) planAgentProvider::get,
                        SubAgentConfig.builder()
                                .toolName("itinerary_plan_agent")
                                .description("调用 ItineraryPlanAgent 处理审批通过后的行程规划、交通/酒店搜索比价与预订。参数：message（任务描述），可选 session_id（继续会话）。")
                                .forwardEvents(false)
                                .build())
                .apply();
```

它在 MasterAgent.build() 执行时（这时当前线程的 ThreadLocal 里有 sessionCtx）就把 sessionCtx 抓出来存进 lambda 对象的字段里。

等后面在 boundedElastic-1 上执行时，lambda 会先 AgentSessionContextHolder.set(captured) 把值塞到 boundedElastic-1 的 ThreadLocal 里，再调 getBean → createToolCtx() 就能读到值了。

```text
public static <T> Supplier<T> bind(Supplier<T> supplier) {
    // 在"有值的线程"上、注册那一刻抓走
    AgentSessionContext captured = get();          
    if (captured == null) {
        return supplier;                           
    }
    // 执行时再贴回执行线程
    return () -> callWith(captured, supplier);     
}

public static <T> T callWith(AgentSessionContext context, Supplier<T> supplier) {
    if (context == null) {
        return supplier.get();
    }
    AgentSessionContext previous = get();
    if (previous == context) {
        return supplier.get();                     
    }
    
    //把之前的线程的变量，保存到当前线程中
    set(context);
    try {
        return supplier.get();
    } finally {
        // 还原执行线程原有状态，
        if (previous != null) {    
            //  避免把上下文泄漏进线程池                
            set(previous);                         
        } else {
            clear();
        }
    }
}
```

TTL为啥不行？

上面的问题第一开始遇到的时候，我想到了是跨线程导致的，于是我第一版使用阿里的TTL做的。他能实现跨线程的ThreadLocal。

但是这个方案也有问题。

`boundedElastic` 的 worker 是**懒创建**的。第一次请求时，`boundedElastic-1` 由携带上下文的那个线程创建出来， `InheritableThreadLocal` 在**线程构造那一刻**把父线程的值拷进了新线程。所以：

- 单人联调、或服务刚启动后的第一个会话 → **必然通过**。这不是巧合，机制是真实的。
- 所以"我实测能用"这个观察是对的，只是它只覆盖了第一个用户。

但是，这里是个线程池啊，worker 复用时，`InheritableThreadLocal` **不会**在任务提交时重新拷贝，值就一直冻在之前的数据上。

`remove()/clear()` 也救不了：清理动作只能清当前线程的副本，子线程继承到的是它自己的一份拷贝，父线程清不掉。而子线程是agentscope内部执行的。。。

后果的严重性要说清楚：`createToolCtx()` 从

读到 null → 打 warn → 工具里 NPE 炸出来

退化成

读到 userA → 静默用 A 的身份查/改 B 的差旅单
