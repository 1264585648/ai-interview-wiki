# ✅为什么要用多智能体架构？

任务太多导致注意力分散

大模型的注意力是有限的。一个 Agent 若同时挂着申请、审批、规划、比价、下单、退票、政策查询、景点查询十几类工具和职责，它在每一步 reasoning 时都要在几十个工具、几段互相矛盾的指令里挑选，注意力被稀释，误选、漏选、来回横跳的概率飙升。

**按职责切分，每个 Agent 只盯一件事，工具集小而聚焦。** **职责越窄，注意力越集中，选错工具的空间越小。**

比如，InfoAgent 只做信息查询，工具集只有政策、目的地资讯和三个 RAG 知识库，没有任何写操作；ItineraryPlanAgent只做规划，SubjectiveAssessorAgent 只做审核，

流程太长导致token 占用太多

差旅是一条长链路：申请 → 审批 → 规划→ 审核报告 → 下单结果  →  信息查询  →  报销。如果这些全塞进同一条对话历史，多轮之后上下文迅速膨胀到几十上百 K token，既贵又让模型"记不住重点"。

而如果做成多智能体，那么每个智能体只需要维护自己的上下文就行了，报销智能体不需要关心规划是这么做的，他只需要负责完成指定发票的报销即可。关注点更少，上下文更省。

不能给每个任务用不同模型

单 Agent 只能绑定一个模型，无法因任务而变。而一个差旅任务可能涉及到很多操作，有的可能需要强一点的模型，有的可能基本模型就够了，一句"杭州出差补贴多少"用顶配思考模型秒回是浪费；而多方案比价、风险权衡用便宜模型又力不从心。

所以，拆分成多智能体， 可以更加精细化的控制每一个智能体用到的模型，甚至是针对性的调整模型参数，可以更加好的优化模型效果与成本。

规划和反思放一起，起不到作用

如果让同一个 Agent、同一个模型既做规划又做自审，等于让它给自己的答案打分——它天然倾向于确认自己"我觉得没问题"，反思形同虚设（自我确认偏误）。

我们用多智能体，**"规划"和"审核"拆成两个 Agent，且刻意用不同模型。**

ItineraryPlanAgent（规划者，强模型 + 深度思考）在方案确认前，把审核通过工具编排**委托**给独立的 SubjectiveAssessorAgent 子智能体（后面改成用ItineraryReviewTools来编排主观+客观审核了）。

"出题的"用强模型 + 思考，"批卷的"用另一档模型，两者不是同一个大脑。这样反思才有独立视角、才真正能挑出问题。**规划与反思的分离，只有多智能体才能自然表达——单 Agent 里没有"换个脑子再审一遍"的位置。**

工具全暴露 → 用错工具 / 不知道用哪个

工具越多，模型越容易选错，也越容易被诱导去调用它本不该碰的高危工具（比如查询场景下误触"下单出票"）。工具暴露面 = 风险面。

如果只有一个智能体，必然需要把几十个工具都给模型注册上去，大大的增加模型选错的概率。

**给每个 Agent 只暴露它该有的工具，模型的选择空间小了，选错和越权同时被摁住——这是"最小权限原则"在 Agent 上的落地，单 Agent 无法表达这种阶段性权限收敛。**

提示词打架，人格不统一

每一个智能体我们都会在提示词中给他做角色定位，"你是只读信息助手，不要做任何变更"和"你是下单执行专家，确认后立刻出票"。但是如果是但智能体，这两套人格塞进一个 system prompt，模型会精神分裂，行为不可预测。

而如果不做角色定位，他就会丢失人格，解决问题就会没有那么好的确定性。

**多智能体则没有这个烦恼，每一个智能体有自己的提示词，都有独立人格，更专注解决单一问题。**
