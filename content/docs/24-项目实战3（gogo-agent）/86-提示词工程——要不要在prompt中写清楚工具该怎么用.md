# ✅提示词工程——要不要在prompt中写清楚工具该怎么用？

Agent开发中，工具无疑是至关重要的，Agent需要用工具来帮我们解决问题。我们用的框架，包括其他的各种框架，他们都会在工具注册后，自动将工具的名称、参数格式（JSON Schema）和基础描述注入到提示词中。

那么，如果是这样的话，我们还需要自己在我们的system prompt中写清楚关于工具该怎么调用吗？

其实是有必要的。

因为框架自动注入的提示词相当于是这解决的是**“能力”**问题（模型知道有哪些工具、参数怎么填），而我们自己写 Prompt 解决的是**“策略”**问题（模型知道在什么情况下、按什么顺序、遵循什么规矩去用这些工具）。

打个比方：框架自动注入的工具信息，就像是你给新员工发了一套**“工具箱”**；而你自己写的 Prompt，则是给这位新员工的**“岗位操作手册”和“业务指导”**。

所以，提示词中不需要重复写工具的定义和参数怎么组装，而是重点写以下内容更合适

**写清楚****什么时候用**

框架只知道你有一个 `search_web` 工具，但它不知道你的业务逻辑。

- **框架自动注入的：** “`search_web`：用于搜索互联网信息。”
- **你需要补充的：** “当用户询问**最新的实时新闻**或**股价**时，必须调用 `search_web`；但对于简单的常识性问题（如‘1+1等于几’），**禁止调用任何工具**，直接回答即可。”（这一条随着LLM越来越强，很多时候也不需要了）
- **多工具协同：** 如果你有多个相似工具，框架无法替你做业务取舍。你需要告诉它：“已知文件路径时直接读取文件；不知道路径但知道关键词时，优先使用文本搜索工具。”

**写清楚****怎么用**

为了让你的后端代码能稳定解析 Agent 的输出并执行工具，你需要强制模型按照特定的格式输出。

- **框架自动注入的：** 工具的 JSON Schema 定义。
- **你需要补充的：** 思维链引导和结构化输出要求。例如，你需要在 Prompt 中规定：“请严格按照 `Thought（思考） -> Action（行动） -> Observation（观察）` 的逻辑进行推理，并且 Action 部分必须输出标准的 JSON 格式，以便系统解析。” 如果不写清楚，模型可能会用自然语言回复“我决定调用搜索工具”，导致你的代码无法解析执行。

**告诉他有哪些****规矩**

这是框架完全无法替代的部分，它决定了 Agent 的“性格”和“底线”。

- **人设与目标：** “你是一个专业的金融分析助手，你的目标是提供客观的数据分析……”
- **安全边界：** “严禁调用 `delete_file` 工具”、“在调用任何涉及资金转账的工具前，必须先向用户确认”。
- **容错机制：** “如果工具调用失败或返回空结果，请尝试更换关键词重新搜索，而不是直接放弃。”

gogo-agent 的答案不是"全写提示词"也不是"全靠工具描述"，而是一条清晰的分工线：

- **工具能做什么、参数长什么样、以及工具自身不可分割的前置条件** → 写进 @Tool/@ToolParam 描述与 Skill 正文（工具的"自描述"）。
- **多个工具之间的编排——调用顺序、时机、分支选择、几轮循环、何时停** → 写进系统提示词（Agent 的"作业流程"）。

同样是政策的两个工具，"到底该用哪个"这个**场景决策**，一个字都不在 @Tool 描述里，而是在信息查询提示词里用一张决策速查表讲清（info-agent-system.md）：

```text
## 政策查询双通道说明
差旅政策类查询**必须**根据场景选择正确的通道，**严禁混用、错用**：
### 通道决策速查
| 用户问题特征 | 优先通道 |
|---|--|
| "差旅制度里关于 X 是怎么规定的？" | 政策知识库 |
| "我**去 X 城市**的住宿标准？" / "我**的**差旅标准？" | PolicyTools.query_travel_policy |
| "我订的酒店超标吗？" / "帮我检查这个行程" | PolicyTools.check_travel_policy |
```

行程规划提示词更是一份"编排剧本"：先查已审批单、再取偏好和政策、然后懒加载搜索技能、组装参数调 plan_itinerary、送审、按需修复最多两轮、最后停下等用户——这些**跨工具的先后与循环**全在提示词，工具本身都不知道自己在流程的第几步（itinerary-plan-agent-system.md）：

```text
1. **开始行程规划前，优先调用 query_travel_order(status="APPROVED") 查询已审批差旅单**   （L11）
2. **先获取用户偏好和差旅政策**，再生成方案                                              （L61）
3. **规划阶段只使用 search Skills**，不得调用 booking 相关工具                            （L65）
   - **懒加载搜索技能（重要）**：...必须在本步骤开始时才通过 load_skill_through_path 加载 （L68）
7. **修复（重跑，禁止 yy）**：...最多 2 轮修复                                            （L79）
```

连"何时该停止调工具"这种纯编排约束也在提示词，而非工具（itinerary-plan-agent-system.md）：

```text
7. **方案输出后必须停止，等待用户确认（最高优先级约束）**：
   - 输出最终方案 Markdown 后，**禁止在同一轮继续调用任何工具**
```
