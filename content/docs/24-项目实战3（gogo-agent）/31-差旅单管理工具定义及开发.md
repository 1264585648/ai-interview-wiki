# ✅差旅单管理工具定义及开发

关于差旅的管理，我们提供了**两组工具（读 + 写）**：本项目把"查"和"改"物理拆成两个 Bean，好处见后面。

- TravelOrderReadTools：只暴露一个 query_travel_order。
- TravelOrderWriteTools：暴露四个——submit_travel_approval / query_approval_status / cancel_travel_order / modify_travel_order。
- 另外还有一个 TravelOrderConflictTools.check_travel_order_conflicts（跨差旅单的时间/衔接冲突检测），本文点到即止不深入，聚焦"CRUD 主链路"。

**"读工具在多个 Agent 复用，写工具只在一个 Agent 上"**：TravelOrderReadTools 挂在 BaseSubAgent 上，被 ItineraryManageAgent / ItineraryPlanAgent / BookingAgent 共用；TravelOrderWriteTools 仅注册到 ItineraryManageAgent——写权限收敛在一个 Agent，比"到处都能改"要安全得多。

```text
@Component
public class TravelOrderReadTools {

    @Autowired private TravelOrderRepository travelOrderRepository;
    @Autowired private TravelOrderMapper travelOrderMapper;   // 复杂多条件查询直接用 MP 的 mapper

    @Tool(name = "query_travel_order",
          description = "查询用户差旅单列表或指定差旅单详情。支持按状态、出发日期范围过滤。")
    public String queryTravelOrder(
            AgentSessionContext sessionCtx,                      // ← 框架注入，userId 从这拿
            @ToolParam(name = "order_id",
                    description = "差旅单ID，传入则直接返回该单详情，忽略其他筛选条件",
                    required = false) String orderId,
            @ToolParam(name = "status",
                    description = "状态过滤，支持单个或逗号分隔的多个状态，如 DRAFT 或 DRAFT,SUBMITTED。"
                                + "可选值: DRAFT/SUBMITTED/APPROVED/REJECTED/COMPLETED/CANCELLED",
                    required = false) String status,
            @ToolParam(name = "start_date", description = "筛选出发日期不早于此日期的差旅单，格式 YYYY-MM-DD，可选",
                    required = false) String startDate,
            @ToolParam(name = "end_date",   description = "筛选出发日期不晚于此日期的差旅单，格式 YYYY-MM-DD，可选",
                    required = false) String endDate) {

        // ① 拿 userId：从会话上下文，LLM 不需要知道
        String userId = sessionCtx.getUserId();

        // ② 精确查：传了 orderId 就走 selectById；顺手把 orderId 写进会话上下文
        //   —— 这一步至关重要：BookingPersistenceHook 会读这个字段，
        //   把 tuniu-CLI 后续产生的预订记录反向关联到"当前操作的差旅单"
        if (orderId != null && !orderId.isBlank()) {
            TravelOrder order = travelOrderRepository.findByOrderId(orderId).orElse(null);
            if (order != null) {
                sessionCtx.setTravelOrderId(orderId);
            }
            return JSON.toJSONString(order != null ? order : "{\"error\":\"order not found\"}");
        }

        // ③ 列表查：根据 date / status 是否给出，选择走 Repository 快捷方法 or 拼 LambdaQueryWrapper
        List<TravelOrder> orders;
        boolean hasDateFilter = (startDate != null && !startDate.isBlank())
                             || (endDate   != null && !endDate.isBlank());

        if (hasDateFilter) {
            LambdaQueryWrapper<TravelOrder> wrapper =
                    new LambdaQueryWrapper<TravelOrder>().eq(TravelOrder::getUserId, userId);
            if (status != null && !status.isBlank()) {
                List<TravelOrderStatus> statusList = parseStatusList(status);
                if (statusList == null) {
                    return JSON.toJSONString(Map.of("error",
                            "无效的状态参数: " + status + "，可选值: DRAFT/SUBMITTED/APPROVED/REJECTED/COMPLETED/CANCELLED"));
                }
                if (statusList.size() == 1) wrapper.eq(TravelOrder::getStatus, statusList.get(0));
                else                        wrapper.in(TravelOrder::getStatus, statusList);
            }
            if (startDate != null && !startDate.isBlank()) wrapper.ge(TravelOrder::getDepartureDate, startDate);
            if (endDate   != null && !endDate.isBlank())   wrapper.le(TravelOrder::getDepartureDate, endDate);
            wrapper.orderByAsc(TravelOrder::getDepartureDate);
            orders = travelOrderMapper.selectList(wrapper);
        } else if (status != null && !status.isBlank()) {
            // 略：只按状态过滤，同样支持逗号分隔的多状态
            // ...
        } else {
            orders = travelOrderRepository.findByUserId(userId);
        }

        return JSON.toJSONString(orders);
    }

    /** 解析逗号分隔的状态字符串，非法值返回 null 让上层生成友好错误 */
    private List<TravelOrderStatus> parseStatusList(String status) { /* ... */ }
}
```

TravelOrderWriteTools

TravelOrderWriteTools.java 是本文最重的一个类，四个 @Tool 完成 CRUD 中的"C/U/D + 查审批"。这里按业务动作各自展开。

写工具没有把结果糊成一份 Map&lt;String, Object&gt;，而是**每种响应定义一个 Record**：

```text
record ErrorResult(boolean success, String errorCode, String message) {
    static ErrorResult of(String errorCode, String message) {
        return new ErrorResult(false, errorCode, message);
    }
}

/** 需用户二次确认的拦截响应（APPROVED 状态下取消/修改都会走这里） */
record ConfirmRequiredResult(boolean success, boolean needConfirm,
                             String orderId, String currentStatus, String message) {}

record SubmitResult(boolean success, String orderId, String processInstanceId,
                    String orderStatus, String approvalStatus, String submitTime,
                    String destination, String departureCity, String departureDate,
                    String returnDate, String purpose, String message) {}

record QueryApprovalResult(boolean found, String queryMode, String processInstanceId,
                           String orderId, String userId, String title, String status,
                           String submitTime, String updateTime, String remark, String message) {}

record BookingSummary(String bookingId, String bizType, String title,
                      String status, String externalOrderNo) {}

record CancelResult(boolean success, String orderId, String orderStatus,
                    boolean approvalCancelled, String cancelledApprovalId, String reason,
                    String message,
                    List<BookingSummary> associatedBookings, String affectedBookingsMessage) {}

record ModifyResult(boolean success, String orderId, String orderStatus, String oldApprovalId,
                    boolean oldApprovalCancelled, String newApprovalId, String newApprovalStatus,
                    String updatedFields, String message,
                    List<BookingSummary> associatedBookings, String affectedBookingsMessage) {}
```

两个好处：

1. **对 LLM 友好**：字段名 snake_case（success / order_id / need_confirm），LLM 一看就明白语义，能直接把 message 抽出来讲给用户。
2. **对开发者友好**：Java 侧编译期强类型，改字段名/加字段一个 IDE refactor 就搞定。

**submit_travel_approval**

这是全项目最重的一个"业务事务"，但 Tool 层的代码在重构后异常干净——**校验、幂等在上、Service 一句、verify 收尾**

```text

      description = "xxxxxxx")
public String submitTravelApproval(AgentSessionContext sessionCtx,
        @ToolParam ....) {

    String userId = sessionCtx.getUserId();

    // ── 入参校验：非空 + 日期格式 + 起止顺序 
    // 幂等处理：相同要素 + 处于生效状态 (DRAFT/SUBMITTED/APPROVED) 已存在 → 直接返回已有单
    // ①②③ 创建差旅单 + 提交审批单 + 双向关联 —— 全部委托给 Service，
    // ④ 事务提交后查库验证：状态真的落到 SUBMITTED 了才算成功
    }
}
```

抓四个设计动作：

1. **幂等**：findDuplicateActiveOrder 用 (userId, destination, departureCity, departureDate, returnDate, purpose) 六元组做 in-memory 精确比对。命中直接返回已有单，避免"用户连点两次确认""LLM 幻觉重发一次"这类重复提交——**并且这一步是纯查询，放在事务外面正确**（幂等命中本来就无需事务）。

1. **三步写库委托给 ****travelOrderService.createAndSubmit(order)**：这是本次重构的核心。@Transactional(rollbackFor = Exception.class) 会让三步写库跑在同一个本地事务里
2. **sessionCtx.setTravelOrderId(orderId)**** 在幂等命中和事务成功后各写一次**：确保后续 booking 能挂到正确差旅单。
3. **verifyOrderStatus 做事后查库验证**：即使事务提交了，也再回查一次状态。这是**双保险**——主要是为了避免模型幻觉。明明插入失败了，但是他还是认为成功了。

**cancel_travel_order**

```text
入参校验 → 查库 → 权限校验(userId 匹配)
    ↓
    ├─ CANCELLED     → INVALID_STATE "已取消"
    ├─ COMPLETED     → INVALID_STATE "已完成不可取消"
    ├─ APPROVED && !force → ConfirmRequiredResult  ← 二次确认拦截
    └─ 其余状态 或 APPROVED&&force
         ↓
    ① travelOrderService.cancelWithApproval(order)      ← 事务原子
       │ 内部：updateStatus(CANCELLED) + approvalService.cancel(approvalId)
       │ 若差旅单上没存 approvalId，则回查 findLatestByOrderId 兜底
       └ 返回 CancelOutcome(orderCancelled, approvalCancelled, cancelledApprovalId)
    ② verifyOrderStatus(orderId, CANCELLED)             ← 事后校验
    ③ queryAssociatedBookings(userId, orderId)          → List<BookingSummary>
    ④ buildAffectedBookingsMessage(bookings)            → 拼一句"该行程存在 N 条关联预订..."
    ↓
    return CancelResult(true, ..., associatedBookings, affectedBookingsMessage)
```

关键代码：

```text
if (TravelOrderStatus.APPROVED == currentStatus && !Boolean.TRUE.equals(force)) {
    return toJson(new ConfirmRequiredResult(false, true, orderId, currentStatus.getCode(),
            "该差旅单已审批通过，取消后不可恢复且可能影响已预订行程。"
          + "请用户明确确认后再操作（传入 force=true）。"));
}

// 取消差旅单并同步撤销关联审批单，由 @Transactional 保证原子性
TravelOrderService.CancelOutcome outcome = travelOrderService.cancelWithApproval(order);
if (!outcome.orderCancelled()) {
    return toJson(ErrorResult.of("UPDATE_FAILED", "差旅单状态更新失败，请稍后重试。"));
}
boolean approvalCancelled  = outcome.approvalCancelled();
String  cancelledApprovalId = outcome.cancelledApprovalId();

// 事后校验
String cancelVerifyErr = verifyOrderStatus(orderId, TravelOrderStatus.CANCELLED, "cancel_travel_order");
if (cancelVerifyErr != null) return cancelVerifyErr;

// 查询关联预订记录（排除已 CANCELLED/REFUNDED）
List<BookingSummary> associatedBookings = queryAssociatedBookings(userId, orderId);
String affectedMsg = buildAffectedBookingsMessage(associatedBookings);

return toJson(new CancelResult(true, orderId, TravelOrderStatus.CANCELLED.getCode(),
        approvalCancelled, cancelledApprovalId, reason, msg,
        associatedBookings, affectedMsg));
```

工具**不会自动取消关联预订**，而是把预订清单摘要返回给 LLM，让 LLM 转述给用户拿确认，用户同意再调 cancel_booking(booking_id)。这里体现的原则是——"**只做原子动作，副作用由用户决定**"，避免"取消一个差旅单顺手退掉五张机票"这类不可撤销的连锁反应。

**modify_travel_order**

```text
入参校验（可选字段的日期格式）→ 查库 → 权限校验
    ↓
    状态门禁（CANCELLED/COMPLETED 拒绝，APPROVED 需 force=true）
    ↓
    ⓪ 幂等短路：所有提交字段与当前值一致 → 直接返回 ModifyResult(updatedFields="无字段变更")
    ↓
    ① 更新有变化的字段（in-memory）
    ↓
    ② travelOrderService.modifyAndResubmit(order)   ← 事务原子
        内部：cancel 旧审批 → save DRAFT + approvalId=null → submit 新审批 → save SUBMITTED
        返回 ModifyOutcome(oldApprovalId, oldApprovalCancelled, newApproval)
    ③ verifyOrderStatus(orderId, SUBMITTED)         ← 事后校验
    ④ 查关联预订 + 拼副作用消息
    ↓
    return ModifyResult(oldApprovalId, newApprovalId, updatedFields, associatedBookings, ...)
```

关键代码片段：

```text
// ⓪ 幂等短路：五个字段全都"要么为空要么等于当前值" → 无变化，跳过撤审重提
boolean noChange = (isBlank(destination)   || equalsSafe(destination,   order.getDestination()))
        && (isBlank(departureCity)         || equalsSafe(departureCity, order.getDepartureCity()))
        && (isBlank(departureDate)         || equalsSafe(departureDate, order.getDepartureDate()))
        && (isBlank(returnDate)            || equalsSafe(returnDate,    order.getReturnDate()))
        && (isBlank(purpose)               || equalsSafe(purpose,       order.getPurpose()));
if (noChange) {
    String currentApprovalId = order.getApprovalId();
    return toJson(new ModifyResult(true, orderId, order.getStatus().getCode(),
            currentApprovalId, false, currentApprovalId, null,
            "无字段变更", "提交的信息与当前差旅单一致，未做任何修改。", List.of(), null));
}

// ①：字段变更 in-memory 更新到 order
if (!isBlank(destination))   order.setDestination(destination);
if (!isBlank(departureCity)) order.setDepartureCity(departureCity);
// ... 其他字段同理

// ② 撤销旧审批 + 保存字段变更 + 提交新审批 + 关联新审批，由 @Transactional 保证原子性
TravelOrderService.ModifyOutcome outcome = travelOrderService.modifyAndResubmit(order);
String oldApprovalId          = outcome.oldApprovalId();
boolean oldApprovalCancelled  = outcome.oldApprovalCancelled();
ApprovalRecord newRecord      = outcome.newApproval();

// ③ 事后校验
String modifyVerifyErr = verifyOrderStatus(orderId, TravelOrderStatus.SUBMITTED, "modify_travel_order");
if (modifyVerifyErr != null) return modifyVerifyErr;
```

Service 里 modifyAndResubmit 走"cancel 旧审批 → save DRAFT + approvalId=null → submit 新审批 → save SUBMITTED"四步，全部在同一个 @Transactional 里。

**TravelOrderStatus**

```text
public enum TravelOrderStatus {
    DRAFT    ("DRAFT",     "草稿"),
    SUBMITTED("SUBMITTED", "审批中"),
    APPROVED ("APPROVED",  "已通过"),
    REJECTED ("REJECTED",  "已拒绝"),

    CANCELLED("CANCELLED", "已取消");
}
```

会话上下文里的 travelOrderId

AgentSessionContext作为会话上下文，其中有一个travelOrderId。

TravelOrderReadTools.queryTravelOrder（精确查命中时）、TravelOrderWriteTools.submitTravelApproval（幂等命中 + 新建成功）这些操作都会写入这个值。

BookingPersistenceHook —— 当 execute_shell_command 触发 tuniu-CLI 完成预订后，Hook 在把 BookingRecord 落库前会读这个值。因为这时候需要保存booking_record，需要通过这个travel_order_id来关联travelOrder
