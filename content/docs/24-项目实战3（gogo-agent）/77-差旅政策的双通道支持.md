# ✅差旅政策的双通道支持

在我们提供的InfoAgent的 ReAct 循环里，LLM 有两种方式获取差旅相关知识：

- **RAG**：把制度文档切成片段、向量化，运行时按语义召回最相关的几段，交给 LLM 组织语言回答。这种方案适合“出差多久后需要提交报销”“差旅管理制度对超标住宿是怎么规定的？” “报销要走什么流程？”这类通用类政策问题。
- **Tool**：把查询数据库操作封装成 @Tool，LLM 在需要时按签名传参调用，拿到结构化 JSON。它适合“我去北京出差酒店住宿每天可以多少”这种和用户强相关的问题。

如果把所有政策问题都交给 RAG，模型容易从制度片段里“脑补”出某个职级 / 城市的具体额度；如果都交给 Tool，制度解释类问题又无法覆盖。

gogo-agent 的解法是在 InfoAgent 里同时装配这两条路，并在 system prompt 里写明“什么时候走哪条、冲突时听谁的”。这就像同时给员工一本《员工手册》和一个 HR 系统账号：前者回答“制度怎么写”，后者回答“我的额度是多少”。

InfoAgent同时挂载知识库与政策工具

工具写完，还要让 Agent 认识它：

```text
@Configuration("infoAgentConfiguration")
public class InfoAgent extends BaseSubAgent {

    private static final int MAX_ITERATIONS = 5;

    @Autowired @Qualifier("attractionKnowledge")
    protected Knowledge attractionKnowledge;
    // ← 政策 RAG 知识库
    @Autowired @Qualifier("corporateTravelPolicyKnowledge")
    protected Knowledge corporateTravelPolicyKnowledge;         
    @Autowired @Qualifier("corporateTravelGuidelinesKnowledge")
    protected Knowledge corporateTravelGuidelinesKnowledge;

    @Bean(name = "infoAgent")
    @Scope("prototype")
    public ReActAgent build() {
        Toolkit toolkit = new Toolkit();

        toolkit.createToolGroup(TOOL_CIRCUIT_BREAKER_GROUP, TOOL_CIRCUIT_BREAKER_GROUP, true);

        toolkit.registration().tool(infoQueryTools).apply();
        toolkit.registration().tool(policyTools).apply();       // ← 政策工具在这里挂上
        toolkit.registration().tool(destinationLiveTools).group(TOOL_CIRCUIT_BREAKER_GROUP).apply();
        toolkit.registration().mcpClient(weatherMcpClient).enableTools(weatherMcpEnabledTools).apply();
        toolkit.registration().mcpClient(oriznVisaMcpClient).enableTools(oriznMcpEnabledTools).apply();

        return ReActAgent.builder()
                .name("InfoAgent")
                .description("信息查询助手，负责查询差旅政策标准、目的地旅游景点、签证入境政策及通用公共信息")
                .model(stableModel)
                .toolkit(toolkit)
                .toolExecutionContext(createToolCtx())     // ← ThreadLocal → ToolCtx 的桥
                .memory(AgentMemoryFactory.create(stableModel))
                .hooks(List.of(dynamicTimeInjectionHook, new AutoContextHook(),
                        cliResultCompressHook, toolCircuitBreakerHook,
                        executionLoggerHook, progressNotifierHook,
                        sessionPersistenceHook, new PendingToolRecoveryHook()))
                .sysPrompt(PromptLoader.loadStatic("info-agent-system.md"))
                .maxIters(MAX_ITERATIONS)
                .knowledge(attractionKnowledge)
                .knowledge(corporateTravelPolicyKnowledge)  // ← 通道 1 的 RAG 也挂上
                .knowledge(corporateTravelGuidelinesKnowledge)
                .toolExecutionConfig(getToolConfig())
                .ragMode(RAGMode.AGENTIC)
                .generateOptions(getGenerateOptions())
                .build();
    }
}
```

三个可对比的装配决策：

- **PolicyTools**** 没有挂在 ****TOOL_CIRCUIT_BREAKER_GROUP**** 里**（destinationLiveTools 挂了），意味着它不参与"外部实时数据熔断降级"——因为政策查询是本地数据库调用，重试/降级由业务侧异常来处理即可，不需要 Hook 参与。
- **政策工具和政策 RAG 知识库并存**：这就是"双通道"能存在的技术基础，工具和 knowledge 是 InfoAgent 同时具备的两个能力。
- **ragMode(RAGMode.AGENTIC)**：让 LLM 自己决定"要不要检索、检索什么"，与 GENERIC 模式（每轮自动注入）相对；这样在纯政策工具就能回答的场景，不会浪费一次 embedding 查询。

让 LLM 知道什么时候用工具

工具挂上去只完成了"能力"这一半，另一半是"教会 LLM 什么时候用"。src/main/resources/prompts/info-agent-system.md 里有一段专门讲双通道：

```text
## 政策查询双通道说明

差旅政策类查询**必须**根据场景选择正确的通道，**严禁混用、错用**：

### 通道 1：政策知识库（RAG 通道）
- **适用场景**：用户询问**通用差旅规则**的语义类问题
  （如"差旅管理制度对超标住宿是怎么规定的？""差旅报销要走什么流程？"）
- **重要约束**：
  - 召回内容是**参考**，不要复述为权威标准
  - 召回为空时直接告知用户"暂未收录该政策"，**不要编造**

### 通道 2：政策工具 `PolicyTools`（工具调用通道）
- **适用场景**：
  - 用户问"**我**去 X 城市**的**住宿标准"——需要与用户身份绑定的精确数据，
    走 `query_travel_policy`
  - 用户问"我订的酒店超标吗？""帮我检查这个行程"——走 `check_travel_policy`
    做实时合规校验

### 通道决策速查
| 用户问题特征    | 优先通道         |
|---------------|----------------|
| "差旅制度里关于 X 是怎么规定的？"  | 政策知识库  |
| "我**去 X 城市**的住宿标准？" / "我**的**差旅标准？" | `PolicyTools.query_travel_policy` |
| "我订的酒店超标吗？" / "帮我检查这个行程"| `PolicyTools.check_travel_policy` |

### 冲突解决
如果用户问题同时满足多个通道的适用场景，请优先选择通道 2 ...
如果两个通道都未返回结果，则返回"暂未收录该政策"。请用户联系 HR 团队。
```

三个我认为写得好的地方：

1. **锚点词很具体**："我""我的""我去"这些第一人称词是明确的身份信号，LLM 拿来做通道选择非常准。
2. **给出冲突仲裁规则**：不留模糊——两个通道都能答时优先工具。这条如果不写，LLM 遇到"我去上海的酒店有什么规定？"这种双意图问题会左右摇摆。
3. **兜底话术显式规定**：都拿不到时说"暂未收录该政策"，避免编造。

同一提示词还有一条全局约束值得注意（第 78 行）：

**禁止向用户暴露内部实现细节**：面向用户的回复中不得出现工具函数名（如 query_travel_policy 等 snake_case 名称）……

也就是说，@Tool.name 是给 LLM 用来路由的、写代码用来注册的，**不是给终端用户看的字符串**——回复里必须换成"差旅政策查询"这样的自然语描述。
