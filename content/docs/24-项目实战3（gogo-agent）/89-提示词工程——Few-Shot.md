# ✅提示词工程——Few Shot

在提示词工程的所有技巧中，Few-shot（少样本示例）几乎是唯一"你可以偷懒但仍然管用"的技巧——因为它把复杂规则的表达外包给了具体样本。

一个例子胜过千言万语的规则。当你要教 LLM 分类意图时，与其写 20 条抽象判断标准，不如给它看 3 个"输入→输出"的示例，LLM 会通过模式识别自动内化规则。

gogo-agent 的 11 个 prompt 里，几乎每一个都用了 Few-shot 示例。gogo-agent 中的 Few-shot 呈现出三种典型形态，每种对应不同的任务复杂度：

```text
形态一：输入→输出对（标准 Few-shot）
   ↓  适用于分类、改写、抽取等短模型任务
   
形态二：完整输出模板（长样例 Few-shot）
   ↓  适用于富文本生成、复杂结构化文档
   
形态三：正反例对照（判别式 Few-shot）
   ↓  适用于需要区分相似场景的判断题
```

对比案例：

| Agent | Few-shot 形态 | 示例数量 | 任务类型 |
| --- | --- | --- | --- |
| IntentRecognitionAgent | 输入→输出对 | 2 组 | 意图分类 |
| QueryRewritingAgent | 输入→输出对 | 3 组 | 问题改写 |
| ConversationTitleAgent | 输入→输出对 | 2 组 | 标题生成 |
| ItineraryPlanAgent | 完整输出模板 | 1 套详细模板 | Markdown 长文生成 |
| ~~ItineraryReviewAgent~~ | 完整输出模板 | 1 套详细模板 | 审核报告生成 |
| QuestionRecommendationAgent | 正反例对照 | 2 组对照 | 判别式推荐 |
| MasterAgent | 正反例对照 | 多处散落 | 路由决策 |

输入→输出对

标准 Few-shot 是最经典的写法——"输入 X 时，输出 Y"。看起来简单，但要写好有很多讲究。

IntentRecognitionAgent 的示例设计

````text
## 示例

### 示例 1：单意图 - 差旅申请

Rewritten question: `我要申请下周从北京去杭州出差，拜访阿里巴巴。`

Output:
```json
&#123;
  "intents": [
    &#123;
      "intent": "travel_application",
      "target_agent": "itineraryManageAgent",
      "confidence": "high",
      "reason": "用户明确提出出差申请，包含目的地和事由。"
    &#125;
  ],
  "primary_intent": "travel_application",
  "multi_intent": false,
  "overall_reason": "单一差旅申请意图。"
&#125;
````

```text
示例 2：多意图 - 审批通过后的行程规划
Rewritten question: 已经审批通过了，帮我规划一下杭州行程， 要去阿里巴巴和西湖，再查一下那边的酒店。

Output:
&#123;
  "intents": [
    &#123;"intent": "itinerary_planning", "target_agent": "itineraryPlanAgent", ...&#125;,
    &#123;"intent": "hotel_search", "target_agent": "itineraryPlanAgent", ...&#125;
  ],
  "primary_intent": "itinerary_planning",
  "multi_intent": true,
  "overall_reason": "用户一句话包含行程规划和酒店查询两个意图，
   二者有先后依赖关系，先规划再查酒店。"
&#125;
```

这两个示例的设计有几个关键点：

**1. 覆盖对立面** ：示例 1 是单意图，示例 2 是多意图；示例 1 简单，示例 2 复杂。两个示例形成对比，教会 LLM "什么时候 `multi_intent: false` ，什么时候 `multi_intent: true` "。

**2. 输出完全展开** ：不用 `...`  省略号，所有字段都写全。LLM 会照抄格式。

**3. 示例本身即解释** ：`overall_reason`  字段的内容"二者有先后依赖关系，先规划再查酒店"就是在示范该字段应该怎么写。

**标准 Few-shot 的黄金法则**：

1. **数量宜少不宜多**：2-3 个足够，多了浪费 token
2. **示例必须覆盖对立面**：正反、简繁、包含关系形成对比
3. **输入贴近真实用户表达**：不要写"输入 A，输出 B" 这种抽象例子
4. **输出零省略**：所有字段全部展开
5. **示例即隐性规则**：字段值本身就是最好的说明

完整输出模板作为 Few-shot

对于复杂的 Markdown 富文本输出，"输入→输出" 对已经不够用了——因为输入太开放（用户可以问任何问题），而输出结构极其复杂。这时候的策略是**只给一个详尽的输出模板作为参照**。

ItineraryPlanAgent 的模板即示例（后面改到了plan-html这个skill中）

````text
8. **最终返回格式（必须是 Markdown，禁止返回 JSON）**：
   参考模板如下（字段按实际填充，无内容的区块可省略）：

    ```markdown
    ## 🗂️ 差旅行程方案（上海 → 杭州，2026-07-16 去 / 2026-07-18 返）

    ### 🏆 推荐方案 · 综合最佳
    > **为什么是它**：在通过审核的方案里综合分最高（85）...

    | 环节 | 详情 | 费用 |
    |------|------|------|
    | 🛫 去程 | 东航 MU5678，上海虹桥 07:30 → 杭州萧山 09:45，经济舱 | ¥620 |
    | 🛬 返程 | 东航 MU5679，杭州萧山 20:10 → 上海虹桥 22:20，经济舱 | ¥620 |
    | 🏨 酒店 | 全季酒店（西湖店），大床房，2 晚，¥413/晚 | ¥826 |
    | **合计** | **行程耗时 4h05m** ｜ **评分** 时间80/价格90/... | **¥1313** |

    ### 📋 方案对比（需要挑选时看这里）
    | 方案 | 标签 | 去程交通 | ... | 审核 |
    | 方案1 ✅推荐 | 价格最低/时间最短 | ... | ✅ 通过 |
    | 方案2 | 综合最优/最符合偏好 | ... | ❌ 未通过 |

    ### 🔍 方案明细
    - **方案1 · 价格最低/时间最短（✅ 通过）**
      - 去程：东航 MU5678，上海虹桥 07:30 → 杭州萧山 09:45，经济舱 ¥620
      ...
    - **方案2 · 综合最优/最符合偏好（❌ 未通过 → 已修复）**
      - ...
      - ❌ 未通过原因：总价 ¥1730 超预算 ／ 去程公务舱高于政策舱位标准
      - 🔧 修复：换更经济酒店 + 去程降经济舱 
             → 生成【方案2-修复版】并通过审核（总价 ¥1450 / 综合 91）

    ### 👉 下一步
    - **确认方案**：告诉我你选哪套方案（如"确认P1"），我再进入预订流程。
    - **想调整**：告诉我新的条件，我按新条件重新规划并审核。
    ```
````

这段模板本身就是一个 Few-shot——它告诉 LLM"你的输出应该长这样"。

**关键设计**：

1. **具体真实的数值**：不用 xxx、{航班号} 占位符，直接写"东航 MU5678"。LLM 会以真实数据的复杂度为参考。
2. **展示状态分支**：模板里同时展示"通过"和"未通过"两种方案，教会 LLM 如何处理不同状态。
3. **展示修复过程**：把"❌ 未通过原因 → 🔧 修复"的完整过程写在模板里，让 LLM 知道如何呈现动态过程。
4. **注明可省略**："无内容的区块可省略"——给 LLM 灵活度而不失结构。

正反例对照的判别式 Few-shot

有些任务不是"生成什么"，而是"判断哪种情况"——这时候正反例对照比单纯的正例更有教学价值。

QuestionRecommendationAgent 的完美案例

```text
### 示例 1：助手在抛出选择题（**不要用"确定"**）

输入：
用户问题：帮我取消下周三的杭州出差
助手回复：您下周三（2026-07-15）的杭州出差已是"已取消"状态。
您还有 3 个未取消的行程：
1) 7月8日-10日北京QCon 
2) 7月9日-11日北京QCon 
3) 7月11日-13日北京客户会议。
请问您具体想取消哪一个？

快速操作关键词（节选）：
- 确认/继续类：确定、确认、提交、继续、是的、好的...
- 修改/补充类：修改、补充...
- 取消/重新类：不对、取消、重新...

输出：
&#123;"questions": ["取消 7月8日-10日北京QCon会议", 
               "取消 7月9日-11日北京QCon会议", 
               "取消 7月11日-13日北京客户会议", 
               "都不是"]&#125;
```

```text
### 示例 2：助手刚给出方案（**可以用"确定"**）

输入：
用户问题：帮我取消这个月的出差安排
助手回复：已为您查询到当前月份（2026年7月）的差旅安排：
...（表格）...，确定要帮您取消吗？

输出：
&#123;"questions": ["确定", "我再想想", "查询该行程的审批进度"]&#125;
```

1. **表面场景相同**（都是"取消出差"），实质分支不同（一个是选择题，一个是确认题）
2. **标题直接标注差异**（"不要用确定" vs "可以用确定"）
3. **输出完全不同**（选项列表 vs 确认词）

LLM 看完这两个示例，就能理解"快速操作关键词的使用取决于助手回复的阶段"这个抽象规则——**用对比示例比写抽象规则更有效**。

Few-shot 是提示词工程的"最后一公里"

从 gogo-agent 的实践中可以提炼出 Few-shot 设计的核心哲学：

**Few-shot 的本质是"模仿学习"** 。LLM 是一个统计模型，它学到的不是"规则"而是"模式"。抽象规则需要 LLM 二次解释和应用，具体示例可以直接被 LLM 模式匹配复用。所以 Few-shot 的效果几乎总是优于同等长度的抽象规则。

**Few-shot 的价值是"降低歧义"** 。任何自然语言规则都会有歧义空间，而具体示例是消除歧义的最有效手段。当规则说"输出简洁的标题"时，LLM 不知道多长算简洁；当示例给出 `上海出差申请`（6字）、`查询北京到杭州机票`（10字），LLM 就有了明确的长度感。

**Few-shot 的设计是"以少胜多"** 。给 20 个平庸示例不如给 3 个精心设计的示例。精心设计的关键是：覆盖对立面、聚焦边界情况、完全展开输出、真实贴近用户。

**Few-shot 是不可替代的** 。角色定义、结构化约束、行为规则都可以在没有示例的情况下写好，但你无法在没有示例的情况下让 LLM 稳定输出复杂 JSON、复杂 Markdown 或做复杂判别。这就是为什么 gogo-agent 的每一个 prompt 都会花大量篇幅写示例——因为这一步的投入回报率最高。

**写好 Few-shot，你的 prompt 就完成了"最后一公里"。**
