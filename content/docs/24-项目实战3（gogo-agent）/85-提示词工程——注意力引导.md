# ✅提示词工程——注意力引导

大模型不是"读到一句话就一定照做"的程序，它是在一段长文本上做概率加权的注意力分配。提示词越长、约束越多，模型的注意力就越被稀释——排在中间的规则最容易被"读过但没执行"。学术上这被称作 *lost in the middle*：模型对**开头（首因）**和**结尾（近因）**记得最牢，对正文中段最容易失焦。

gogo-agent 是一个多子智能体差旅系统，它的提示词天然很长，比如itinerary-plan-agent-system.md 有 177 行，里面塞了信息补充规则、时间换算表、途经点规则、五维打分心法、Markdown 输出模板、禁词兜底……如果只是把这些要求平铺直叙地写下去，模型极大概率会：把相对时间算错、在方案输出后又擅自调工具下单、在文案里泄露内部工具名、或者干脆编造一套没跑过工具的"修复版"方案。

所以 gogo-agent 的提示词工程里，专门有一套**注意力引导**的写法与运行时机制，目的只有一个：**在模型注意力有限的前提下，用格式、位置、重复、负向指令、运行时注入等手段，把最关键的约束"按"在模型一定会看到、一定会执行的地方。**

优先级/强调标记：给约束标上"权重"

最朴素也最高频的手法：用文字显式声明优先级 + 加粗 + emoji 图标，让某几条约束在视觉与语义上"跳出来"。

行程规划提示词把"输出方案后必须停下"这条最容易被违反的规则，直接冠以最高优先级头衔（itinerary-plan-agent-system.md L84–87）：

```text
7. **方案输出后必须停止，等待用户确认（最高优先级约束）**：
   - 输出最终方案 Markdown 后，**禁止在同一轮继续调用任何工具**——不得调用搜索舱位详情、查联系人等任何动作；
   - **必须完全停止并等待用户下一条消息**：用户确认方案后，由预订专家完成后续下单；
   - **严禁自行替用户做出选择**：即使差旅单已审批、即使只有一套方案通过审核……你仍必须等待用户明确回复。
```

同一份提示词里，"必走闭环""重要""禁止 yy"这类强调词被反复用来给流程节点标权重（L66、L68、L79、L136、L138）：

```text
4. **多目标方案 + 审核 + 修复闭环（必走，不可跳过）**……
      - **懒加载搜索技能（重要）**……**严禁**在最初那批调用里提前加载。
   7. **修复（重跑，禁止 yy）**……**严禁跳过工具、直接在文案里虚构"修复版"方案**
```

要点：优先级标记不是随便加粗，而是**只给"违反成本最高、模型最容易犯"的少数几条**加最高等级。如果满篇加粗，等于没有加粗——注意力权重会重新被拉平。

开头定角色

模型对首尾最敏感，gogo-agent 就把两类最关键信息分别放在**第一行**和**最后一段**。

每个子智能体提示词的第一行都是角色定位，先把"你是谁、只管什么"钉死。

显式告诉模型"不要做什么"

正向指令（"请做 X"）常常拦不住模型的"自作聪明"，gogo-agent 大量使用**负向指令**，点名封死那些模型最爱犯的错误路径。

最典型的是时间换算——模型很爱"自己用日期推星期"，结果算错。

```text
当前日期：{{current_date}}（{{current_weekday}}）。以注入的"星期几"为准，
不要自行从日期推算星期。
```

输出格式强制约束

让模型不跑偏的最有效方式之一，是把输出形状本身变成一条强约束——要么只准 JSON，要么只准 Markdown，二者互斥且反复强调。

结构化注意力：分节/编号/清单/分情况

最后一类是排版层面的：用标题分节、数字编号、清单、"情况一/情况二"分法、"第一步…第四步"流程，把一大段规则切成模型好逐条对齐的小块。

行程规划提示词的核心闭环就是"第 1 步收集 candidates → 第 2 步准备参数 → 第 3 步偏好打分 → 第 4 步一次性规划 → 第 5 步批量审核 → 第 6 步判断修复 → 第 7 步重跑"这样的严格编号流程（L66 起）；信息查询提示词用"通道 1 / 通道 2 + 决策速查表格 + 冲突解决"三段式，把一个容易混用的判断显式表格化（info-agent-system.md L45–71）：

```text
### 通道决策速查

| 用户问题特征 | 优先通道 |
|---|--|
| "差旅制度里关于 X 是怎么规定的？" | 政策知识库 |
| "我**去 X 城市**的住宿标准？" / "我**的**差旅标准？" | PolicyTools.query_travel_policy |
| "我订的酒店超标吗？" / "帮我检查这个行程" | PolicyTools.check_travel_policy |
```

结构化本质上是"降低模型对齐规则的认知负荷"。一张决策表格能让模型一眼把"用户问题特征→该走哪个通道"对齐好，远胜过一整段散文描述——散文里的判断条件很容易被模型漏读一两个。
