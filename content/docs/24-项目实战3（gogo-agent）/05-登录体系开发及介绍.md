# ✅登录体系开发及介绍

我们项目的登录体系基于 **Sa-Token **实现的，会话数据存储在 **Redis**，前端把 Token 持久化在 `localStorage` 并在每个请求头中携带。

整体分层：

| 层次 | 组件 | 职责 |
| --- | --- | --- |
| 配置 | `SaTokenConfigure`+<br>`application.yml` | CORS 过滤器、全局路由鉴权拦截器、Token 策略 |
| 接口 | `LoginController` | `/api/auth/login`、<br>`/logout`、`/info` |
| 业务 | `AuthService`+<br>`UserAccountMapper` | 账密校验、会话创建/销毁、管理员判定 |
| 数据 | `user_account`/`user_profile` | 登录账号与用户档案，一对一关联 |
| 上下文 | `AgentSessionContext(Holder)` | 把 userId 传递到 Agent / Tool / Hook |
| 异常 | `GlobalExceptionHandler` | 未登录 401、无权限 403 的统一 JSON |
| 前端 | `authStore`+`api/auth.ts`+`App.tsx` | 登录态持久化、Token 注入、启动校验 |

核心约定：Sa-Token 的 `loginId` 就是业务 `userId`（如 `u_001`），因此任意一层通过 `StpUtil.getLoginIdAsString()` 即可拿到当前用户，无需再传参。

依赖与配置

Maven 依赖（`pom.xml`）

```xml

<sa-token.version>1.39.0</sa-token.version>
<!-- sa-token-spring-boot3-starter：注解 + 拦截器 -->
<!-- sa-token-redis-jackson：会话持久化到 Redis，重启/多节点不丢登录态 -->
<!-- transmittable-thread-local 2.14.5：跨线程池传递会话上下文 -->
```

Sa-Token 配置

```yaml

sa-token:
  token-name: Authorization   # 前端请求头字段名
  timeout: 2592000            # Token 有效期 30 天
  active-timeout: -1          # 不做活跃续期
  is-concurrent: true         # 允许同一账号多地登录
  is-share: false             # 同端多次登录各自生成独立 Token
  token-style: random-128     # 随机 128 位 Token
  is-print: false
```

要点：`is-concurrent=true` + `is-share=false` 意味着多设备登录互不踢人，且每次登录都是一个新 Token；`active-timeout=-1` 表示不存在"闲置过期"，只有 30 天绝对过期。

CORS 与全局鉴权拦截器

SaTokenConfigure.java中做了两件事，顺序很关键：

1. `CorsFilter`（Servlet Filter 级）：允许所有源/方法/头，暴露 `Authorization`，预检缓存 3600s。放在 Filter 层是为了让浏览器的 `OPTIONS` 预检请求在进入 Spring MVC 拦截器之前就被处理掉。
2. `SaInterceptor`（MVC 拦截器）：

```java

registry.addInterceptor(new SaInterceptor(handle -> {
    SaRouter.match("/**")
            .notMatch("/api/auth/login")
            .check(r -> StpUtil.checkLogin());
}) {
    @Override
    public boolean preHandle(...) throws Exception {
        // OPTIONS 预检请求无 Token，直接放行（CorsFilter 已处理完毕）
        if ("OPTIONS".equalsIgnoreCase(request.getMethod())) {
            return true;
        }
        return super.preHandle(request, response, handler);
    }
}).addPathPatterns("/**");
```

即：除 `/api/auth/login` 与所有 `OPTIONS` 请求外，全站接口都要求登录态。这是一个"默认拒绝"的白名单模型，Controller 上的 `@SaCheckLogin` 属于第二道显式声明（双重保险，也让接口意图自解释）。

数据模型

`user_account`（登录账号）

```sql

CREATE TABLE IF NOT EXISTS `user_account` (
    `id`           BIGINT       NOT NULL AUTO_INCREMENT COMMENT '自增主键',
    `user_id`      VARCHAR(64)  NOT NULL COMMENT '关联 user_profile.user_id',
    `username`     VARCHAR(64)  NOT NULL COMMENT '登录账号',
    `password`     VARCHAR(128) NOT NULL COMMENT '登录密码（生产环境应使用 BCrypt 加密）',
    `real_name`    VARCHAR(64)  DEFAULT NULL COMMENT '用户真实姓名',
    `role`         VARCHAR(16)  NOT NULL DEFAULT 'USER' COMMENT '角色：USER 普通用户 / ADMIN 管理员',
    `created_time` DATETIME     DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_user_id`  (`user_id`),
    UNIQUE KEY `uk_username` (`username`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '用户登录账号表';
```

- `user_id` 与 `username` 双唯一约束：一个业务用户只能有一个登录账号。
- `role` 只有 `USER` / `ADMIN` 两种取值，实体侧通过 `isAdmin()` 判定（忽略大小写）。
- 认证信息（`user_account`）与业务档案（`user_profile`：常驻城市、职级、证件、手机号等，用于机票/酒店预订）**表结构分离**，靠 `user_id` 关联。

认证接口

`LoginController`只有三个接口，都是薄封装：

| 方法 | 路径 | 鉴权 | 请求 | 响应 |
| --- | --- | --- | --- | --- |
| POST | `/api/auth/login` | 白名单放行 | `{username, password}` | `{token, tokenName}` |
| POST | `/api/auth/logout` | `@SaCheckLogin` | 无 | `{message: "退出成功"}` |

`/info` 承担两个作用：既是"取当前用户信息"，也是前端刷新页面时的 **Token 有效性探针**。

AuthService

AuthService是登录体系唯一的业务入口，四个方法：

```java

public String login(String username, String password) {
    UserAccount account = userAccountMapper.findByUsername(username);
    if (account == null || !account.getPassword().equals(password)) {
        throw new IllegalArgumentException("用户名或密码错误");
    }
    // 以 userId 作为 loginId 写入 sa-token 会话（存储于 Redis）
    StpUtil.login(account.getUserId());
    return StpUtil.getTokenValue();
}
```

- `login`：账密校验 → `StpUtil.login(userId)` 建会话 → 返回 Token。校验失败抛 `IllegalArgumentException`，由全局异常处理器转成 400 + "用户名或密码错误"（账号不存在与密码错误返回同一提示，避免账号枚举）。
- `logout`：`StpUtil.logout()` 销毁当前 Token 会话，并打印 userId 日志。
- `isAdmin(userId)`：查库判断 `role = ADMIN`，空/空白 userId 直接返回 false。
- `getRealName(userId)`：给后台审批列表展示提交人姓名用。

密码校验是明文 `equals` 比较，代码与建表注释均明确标注生产环境应改为 BCrypt。

权限

我们只设计了 `USER` / `ADMIN` 二个角色，没有引入 RBAC，也没有使用 `@SaCheckRole`。管理员校验采用**编程式**写法（AdminApprovalController）：

```java

private boolean isAdmin() {
    return authService.isAdmin(StpUtil.getLoginIdAsString());
}

private ResponseEntity<?> forbidden() {
    return ResponseEntity.status(HttpStatus.FORBIDDEN)
            .body(Map.of("message", "无权访问后台管理接口"));
}
```

`/api/admin/approvals`（列表）与 `/api/admin/approvals/{processInstanceId}/decision`（决策）都是 `@SaCheckLogin` + 方法内 `isAdmin()` 双重校验，非管理员返回 403。普通用户侧的**数据隔离**不依赖角色，而是一律以当前登录 userId 作为查询条件。例如 `ChatController` 的历史会话、消息、删除、改标题、反馈接口，以及 `MyTravelController`（注释即写明"仅按 `StpUtil.getLoginIdAsString()` 隔离数据租户"），都把 userId 透传到 Service 层做归属校验。
