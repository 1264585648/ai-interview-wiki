# ✅行程规划的前置拦截

在差旅助手场景中，用户可能发出以下无效请求：

- **行程已过期**：审批单上的出发日期已过或返回日期已过，但用户仍要求"帮我规划行程"。
- **未审批就预订**：用户尚未提交差旅申请或审批未通过，就直接要求"帮我订机票"。
- **差旅单冲突**：用户提交的差旅单与已有生效中差旅单时间重叠、跨城物理不可能。

如果不做前置拦截，LLM 会在无效前提下执行多轮搜索、规划、甚至下单，浪费 Token 和 API 调用成本，还可能产生脏数据。因此需要在 Agent 的关键执行路径上加入**前置校验拦截层**。

技术方案选型：Tool 方案 vs Hook 方案

被放弃的 Hook 方案

最初考虑使用 `PreReasoningEvent` Hook 实现：在每轮推理前注入检查逻辑。

**放弃原因**：

1. **链路过长**：`PreReasoningEvent` → 查库 → 写缓存 → LLM 推理 → 读缓存 → 判断是否继续，涉及 5 个环节。
2. **时序复杂**：Hook 在每轮 Reasoning 前都会触发，需要额外状态判断"是否已检查过"，否则会重复执行。
3. **可调试性差**：拦截逻辑分散在 Hook 和工具两处，出现问题时难以定位。

采用的 Tool 方案：「Prompt 规则 + Tool 检查」

最终方案：在 System Prompt 中写死规则，强制 LLM 在关键步骤前调用专用检查工具，根据返回结果决定是否继续。

**优势**：

1. **链路最短**：LLM 调用工具 → 读返回的 `valid`/`approved` 字段 → 决定是否继续，一步到位。
2. **可调试性强**：工具调用有完整日志，返回值是结构化 JSON，拦截逻辑清晰可见。
3. **零额外状态**：工具内部自包含校验逻辑，不需要 Hook、不需要隐式状态传递。
4. **LLM 自然驱动**：LLM 遵循 Prompt 规则自然调用工具、自然读取结果，无需框架级拦截。

System Prompt 规则

```markdown

2. **行程时间有效性前置检查（最高优先级，不可跳过）**：
   查询到审批单后，**立即调用 `check_travel_time_validity` 检查行程日期有效性**，
   在进入任何搜索、规划步骤之前完成判断：
   - 若返回 `valid=false`：根据 `message` 和 `blocked_orders` 中的原因告知用户行程已开始或已结束，
     **停止所有后续规划动作**。
   - 若返回 `valid=true`：继续执行后续步骤。
   - **例外**：用户明确要求「帮我改签/调整正在进行的行程」等修改类诉求时，可跳过此检查，按需处理。
```

Prompt 规则的关键设计：

- **最高优先级声明**：明确标注"不可跳过"，确保 LLM 不会在信息收集阶段遗漏此检查。
- **条件分支**：给出 `valid=false` 和 `valid=true` 两种返回的明确处理路径。
- **例外场景**：改签类诉求需要操作正在进行的行程，此时不应拦截，避免过度限制。

工具实现

```java

@Tool(name = "check_travel_time_validity",
      description = "检查用户已审批差旅单的行程时间是否仍然有效（未开始/未结束），"
                  + "用于行程规划前的前置校验。"
                  + "返回 valid=true 表示存在可规划的行程，valid=false 表示行程已开始或已结束、无法规划。"
                  + "无参数，自动从会话上下文读取用户身份。")
public String checkTravelTimeValidity(AgentSessionContext sessionCtx) {
    String userId = sessionCtx.getUserId();
    LocalDate today = LocalDate.now();

    // 优先复用会话缓存的 APPROVED 差旅单，避免重复查库
    List<TravelOrder> approvedOrders = sessionCtx.getCachedApprovedOrders();
    if (approvedOrders == null) {
        approvedOrders = travelOrderRepository
            .findByUserIdAndStatus(userId, TravelOrderStatus.APPROVED);
    }

    // 无审批单 → 放行（可规划，只是还没有审批单）
    if (approvedOrders == null || approvedOrders.isEmpty()) {
        return JSON.toJSONString(Map.of(
            "valid", true,
            "today", today.toString(),
            "blocked_orders", List.of(),
            "message", "无已审批差旅单，可直接规划行程。"
        ));
    }

    // 逐条检查审批单日期是否过期
    List<Map<String, Object>> blockedOrders = new ArrayList<>();
    for (TravelOrder order : approvedOrders) {
        String blockReason = evaluateBlockReason(order, today);
        if (blockReason != null) {
            blockedOrders.add(Map.of(
                "order_id", order.getOrderId(),
                "destination", order.getDestination(),
                "departure_date", order.getDepartureDate(),
                "return_date", order.getReturnDate(),
                "reason", blockReason
            ));
        }
    }

    if (!blockedOrders.isEmpty()) {
        return JSON.toJSONString(Map.of(
            "valid", false,
            "today", today.toString(),
            "blocked_orders", blockedOrders,
            "message", String.format("检测到%s的差旅单，无法进行规划。", ...)
        ));
    }

    return JSON.toJSONString(Map.of(
        "valid", true,
        "today", today.toString(),
        "blocked_orders", List.of(),
        "message", "已审批差旅单日期均有效，可继续规划。"
    ));
}
```

拦截判定逻辑

```java

private String evaluateBlockReason(TravelOrder order, LocalDate today) {
    // 返回日期已过 → 行程已结束
    if (today.isAfter(returnDate)) {
        return "行程已结束（返回日期 %s 已过）";
    }
    // 出发日期已到 → 行程已开始
    if (!today.isBefore(departureDate)) {
        return "行程已开始（出发日期 %s 已到达或已过）";
    }
    return null;  // 日期有效，不拦截
}
```

判定规则汇总：

| 条件 | 结果 | 说明 |
| --- | --- | --- |
| 无 APPROVED 差旅单 | `valid=true` | 放行，用户可自由规划 |
| `today > return_date` | `valid=false` | 行程已结束，拦截 |
| `today >= departure_date` | `valid=false` | 行程已开始，拦截 |
| `today < departure_date` | `valid=true` | 行程尚未开始，放行 |

预订前校验

System Prompt 规则

```markdown

2. **审批检查（强制，不可跳过）**：执行预订前，必须调用 `check_travel_order_approval` 检查是否存在已审批通过的差旅单：
   - 若返回 `approved=true`：可执行预订，从返回结果中获取 `order_id`、`destination` 等信息用于后续下单。
   - 若返回 `approved=false`：**直接拒绝预订**，根据 `message` 告知用户
     "差旅单尚未通过审批，无法执行预订。请先提交差旅申请并等待审批通过后再预订。"，
     不得以任何理由绕过此检查。
```

工具实现

```java

@Tool(name = "check_travel_order_approval",
      description = "检查用户是否存在已审批通过的差旅单，用于预订执行前的前置校验。"
                  + "返回 approved=true 表示存在已审批差旅单、可以执行预订，"
                  + "approved=false 表示无审批单、应拒绝预订。"
                  + "无参数，自动从会话上下文读取用户身份。")
public String checkTravelOrderApproval(AgentSessionContext sessionCtx) {
    String userId = sessionCtx.getUserId();

    List<TravelOrder> approvedOrders = sessionCtx.getCachedApprovedOrders();
    if (approvedOrders == null) {
        approvedOrders = travelOrderRepository
            .findByUserIdAndStatus(userId, TravelOrderStatus.APPROVED);
    }

    if (approvedOrders == null || approvedOrders.isEmpty()) {
        return JSON.toJSONString(Map.of(
            "approved", false,
            "message", "差旅单尚未通过审批，无法执行预订。请先提交差旅申请并等待审批通过后再预订。"
        ));
    }

    TravelOrder order = approvedOrders.get(0);
    return JSON.toJSONString(Map.of(
        "approved", true,
        "order_id", order.getOrderId(),
        "destination", order.getDestination(),
        "departure_date", order.getDepartureDate(),
        "return_date", order.getReturnDate(),
        "message", String.format("存在已审批差旅单（%s → %s），可以执行预订。", ...)
    ));
}
```

**设计要点**：

- **语义更清晰**：工具名 `check_travel_order_approval` 直接表达"检查是否可预订"，而非通用查询。
- **结构化返回**：直接返回 `approved` (boolean) 及订单关键信息，LLM 一眼就能判断。
- **不做通用查询**：放弃了在 BookingAgent 中直接调用 `query_travel_order(status="APPROVED")` 的方案，因为通用查询工具的返回是订单列表，LLM 需要自行解析判断"是否有审批单"，不如专用工具直接返回布尔值明确。

会话缓存复用机制

两个前置检查工具共享同一缓存源——`sessionCtx.cachedApprovedOrders`，避免同一会话内重复查库。

缓存写入发生在 `TravelOrderReadTools.queryTravelOrder()` 中：

```java

private void cacheApprovedOrdersIfApplicable(AgentSessionContext sessionCtx,
                                             String status,
                                             List<TravelOrder> orders) {
    boolean includesApproved = status == null
        || status.toUpperCase().contains("APPROVED");
    if (!includesApproved) return;

    List<TravelOrder> approved = orders.stream()
        .filter(o -> o.getStatus() == TravelOrderStatus.APPROVED)
        .toList();
    sessionCtx.setCachedApprovedOrders(approved);
}
```

```java

/**
 * 已审批差旅单缓存：由 query_travel_order 工具在查询 APPROVED 订单时自动写入，
 * 供 check_travel_time_validity 工具读取，避免同一请求内重复查库。
 * volatile 保证并行 Toolkit 下的可见性。
 */
private volatile List<TravelOrder> cachedApprovedOrders;
```
