# ✅方案审核为什么要做成工具而不是单独的子智能体

既然前面说了行程方案的审核不能做成Skill，那么我们把它做成子智能体是不是可以呢？

首先肯定是可行的，而且第一版我们也是这么做的：

但是后来，我还是修改了一下方案，单独创建了一个Tool。但是，大家需要知道的是，subAgent也是通过Tool来实现的，而我这里单独定义一个Tool，而这个Tool的实现中如果有智能体的操作，那么他也算一个子智能体。我为什么要强调这个呢？因为我们就是这么干的。

```
ItineraryPlanAgent
   └─ toolkit 注册了 itineraryReviewTools
        └─ @Tool review_itinerary（代码编排器）
              ├─ safeObjectiveReview()     ← 客观代码评估（6维校验）
              ├─ Pipelines.fanout()        ← 3个主观LLM评估并行
              │     ├─ TripExperienceAssessor ← 体验评估Agent
              │     ├─ ResilienceAssessor   ← 韧性评估Agent
              │     └─ PreferenceAssessor   ← 偏好评估Agent
              ├─ hardVeto 逻辑            ← 代码硬约束否决
              └─ arbitrator.arbitrate()   ← LLM仲裁出整改单
```

这里面有三个LLM主观评估器，TripExperienceAssessor、ResilienceAssessor以及PreferenceAssessor，他们都是基于我代码中单独定义的SubjectiveAssessorAgent实现的。

这么做有几个好处。

硬约束否决不可被 LLM 绕过

在这个方案中，我们硬约束逻辑写在 Java 代码里：

```
boolean hardVetoed = VERDICT_FAIL.equals(objectiveResult.getVerdict());
// ... 客观失败 → 强制 fail，LLM 仲裁器无法推翻
arbitration.setVerdict(VERDICT_FAIL);
```

这段逻辑不在任何 LLM 的 prompt 里，是不可绕过的。如果做成子智能体，"客观审核失败必须否决"这条规则就只能写在 ReviewAgent 的 system prompt 中，LLM 有可能在高上下文压力下忽略它。

并行执行的确定性保障

我们的新方案中用 Pipelines.fanout() 并行跑 3 个主观评估，这是代码级并行，**确定性**地同时发出 3 个 LLM 请求。

```text
fanoutResults = Pipelines.fanout(agents, inputMsg).block();
```

如果是直接挂ReviewAgent 虽然也注册了 itineraryReviewTools，但它本质上还是一个 ReActAgent——它要自己推理决定调哪些工具、以什么顺序调。并行调用取决于 LLM 是否"想到"同时请求多个工具，不确定性高。

Pipelines.fanout() 是 AgentScope 框架提供的一个并行编排原语，用于将同一条消息同时分发给多个 Agent 并行执行，等全部完成后收集结果。本质上 Pipelines.fanout() 就是框架封装好的 Flux.merge() 模式，专门用于 Agent 级别的并行调用，让业务代码更简洁、语义更清晰

Prompt 聚焦度 — "一次只做一件事做得更好"

三个评估器的关注点差异很大，一个关注体验，即通勤时长、作息时间。一个关注韧性，即天气、厌恶风险、缓冲。一个关注偏好，即舱位、酒店、出行时间等。

合成一个 prompt 意味着 120 行 + 天气 + 偏好 + 行程数据 全塞进去，LLM 需要在一次推理中同时 hold 住三种完全不同的评判标准。实际上 LLM 在这种"多角色混合推理"场景下容易出现：

- 注意力稀释：对某个维度的分析草草带过
- 维度交叉污染：用偏好逻辑去评判韧性，或用体验标准去判偏好

最终给出的审核意见很可能是妥协后的结果，而我们把他们三个分开，独立审核，就能做到绝对的公正和独立。也能更好的起到审核的作用。
