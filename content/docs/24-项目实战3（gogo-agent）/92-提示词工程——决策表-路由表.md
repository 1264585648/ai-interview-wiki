# ✅提示词工程——决策表 / 路由表

多智能体系统里最常见的需求是**分流**——把用户的话路由到正确的子智能体、把政策问题选到正确的工具、把"下周三"翻译成正确的日期。这些判断都有一个共性：**条件有限、分支明确**，本质是一张"如果 X → 走 A"的表。

如果把分流逻辑写成纯文本描述（"如果用户问的是通用政策语义类问题就走 RAG，如果是个人标准查询就走工具……"），模型需要做语义理解才能提取判断条件，很容易漏读或混淆。但如果给它一张**对齐好的 Markdown 表格**，判断条件在左列、目标在右列，模型只需要"查表 + 模式匹配"——认知负荷大幅降低，准确率随之提高。

gogo-agent 的提示词体系里，决策表/路由表按功能可分为四大类：意图→子智能体的路由表、场景→工具的选择表、输入→输出的换算表（如相对时间映射）、条件→处理策略的分支表（如冲突分级）。下面逐类展开。

类型 1 —— 意图→子智能体路由表

这是 gogo-agent 里最核心的决策表：把用户意图映射到执行者。这张表在提示词里出现了两次、在代码里出现了一次，三处**互为镜像**——同一张路由逻辑的"给 LLM 看""给 LLM 生成""给代码跑"三种表达。

首先是**意图识别提示词**里的完整映射表——LLM 把用户话分类后必须输出 target_agent，而可选值就是这张表（intent-recognition-agent-system.md）：

| 意图类别 | 说明 | target_agent（camelCase） | 典型触发词/句式 |
| --- | --- | --- | --- |
| `travel_application` | 用户要提交新的差旅申请 / 出差审批 | `itineraryManageAgent` | "我要出差""申请去xx" |
| `travel_cancel` | 用户要取消出差申请或审批单 | `itineraryManageAgent` | "取消出差""不去了" |
| `travel_modify` | 用户要修改差旅申请信息 | `itineraryManageAgent` | "改一下日期""修改目的地" |
| `approval_query` | 用户查询审批进度/状态/结果 | `itineraryManageAgent` | "审批到哪了""批了吗" |
| `travel_order_query` | 用户查询已有差旅单详情/状态 | `itineraryManageAgent` | "我的差旅行程""查一下订单" |
| `itinerary_planning` | 用户要求规划行程、做方案 | `itineraryPlanAgent` | "帮我规划行程" |
| `flight_search` | 用户要查航班 | `itineraryPlanAgent` | "查机票""北京到杭州航班" |
| `train_search` | 用户要查火车 | `itineraryPlanAgent` | "查火车票""高铁" |
| `hotel_search` | 用户要查酒店 | `itineraryPlanAgent` | "查酒店""住哪里" |
| `booking` | 用户要预订/改签/取消已选方案 | `bookingAgent` | "订这个""改签" |
| `reimbursement` | 用户要报销、识别发票、生成报销单 | `reimbursementAgent` | "报销""发票" |
| `policy_query` | 用户查询差旅政策/餐标/签证 | `infoAgent` | "差旅政策""餐标" |
| `attractions_query` | 用户查询目的地景点 | `infoAgent` | "有什么好玩的" |
| `general_info` | 天气/交通/新闻等通用信息查询 | `infoAgent` | "天气怎么样" |
| `greeting` | 用户打招呼、寒暄 | `masterAgent` | "你好""在吗" |
| `unknown` | 无法明确分类 | `masterAgent` | 模糊问题 |

表格右侧的"典型触发词"列非常关键——它不仅帮 LLM 理解每个类别的语义边界，还充当了 few-shot 的压缩形式（不用写完整 example，一列触发词就够了）。

其次是**主控提示词**里的精简版路由表——主控收到意图识别结果后，按这张列表"立即调用"对应子智能体（master-agent-system.md）：

```text
根据意图识别结果**立即**调用对应子智能体，**禁止在路由前向用户提问或确认**：

- `travel_application` / `travel_cancel` / `travel_modify` / 审批相关变更 → `itinerary_manage_agent`
- `approval_query` / `travel_order_query` → `itinerary_manage_agent`
- `itinerary_planning` / `flight_search` / `train_search` / `hotel_search` → `itinerary_plan_agent`
- `booking` → `booking_agent`
- `reimbursement` → `reimbursement_agent`
- `policy_query` / `attractions_query` / `general_info` → `info_agent`
- `greeting` / `unknown` → 由你直接回复
```

类型 2 —— 场景→工具选择表

当一个 Agent 手上有多个功能相似的工具，需要按场景选用时，决策表是最清晰的格式。政策双通道就是典型（info-agent-system.md）：

```text
### 通道决策速查

| 用户问题特征 | 优先通道 |
|---|--|
| "差旅制度里关于 X 是怎么规定的？" | 政策知识库 |
| "我**去 X 城市**的住宿标准？" / "我**的**差旅标准？" | `PolicyTools.query_travel_policy` |
| "我订的酒店超标吗？" / "帮我检查这个行程" | `PolicyTools.check_travel_policy` |

### 冲突解决
如果用户问题同时满足多个通道的适用场景，请优先选择通道2...
如果两个通道都未返回结果，则返回"暂未收录该政策"。请用户联系HR团队。
```

这张表的设计要点：左列不是抽象描述而是**用户原话的模式**（带加粗标记的关键鉴别词"我""去 X 城市""的"），让模型直接用模式匹配做判断而非语义推理；底部补了冲突解决规则和兜底——任何好的决策表都不能只有"正常路径"，还得有"两条都匹配怎么办"和"一条都不匹配怎么办"。

CLI 技能里的意图速查表也属此类（tuniu-cli/SKILL.md）：

```text
| 用户意图关键词 | server | 首选工具 | 必填参数 |
|---------------|--------|----------|----------|
| 航班/机票/飞机 | `flight` | `searchLowestPriceFlight` | `departureCityName`, `arrivalCityName`, `departureDate` |
| 酒店/住宿/民宿 | `hotel` | `tuniuHotelSearch` | `cityName` |
| 火车票/高铁/动车 | `train` | `searchLowestPriceTrain` | `departureCityName`, `arrivalCityName`, `departureDate` |以及服务工具链路表（tuniu-cli/SKILL.md L57–64）——这张不只选工具，还把调用顺序编码在表格里（箭头 →）：
```

```text
| 服务 | 完整流程 |
|------|----------|
| `flight` | `searchLowestPriceFlight` → `multiCabinDetails` → `saveOrder` → `cancelOrder` |
| `hotel` | `tuniuHotelSearch` → `tuniuHotelDetail` → `tuniuHotelCreateOrder` |
| `train` | `searchLowestPriceTrain` → `queryTrainDetail` → `bookTrain` → `cancelOrder` |
```

类型 3 —— 输入→输出换算表

当 LLM 需要做确定性换算（而不是判断/选择）时，决策表退化为"查找表"——给出输入对应的唯一输出。时间处理规则就是典型（time-rules.md）：

```text
1. 用户说相对时间时，必须转换为明确的出发/返回日期：
- "明天"= 当前日期 + 1 天。
- "后天"= 当前日期 + 2 天。
- "3天后 / 三天后 / 3 天后"= 当前日期 + 3 天。
- "大后天"= 当前日期 + 4 天。
- "下周X"= 本周日之后的下一个星期 X；若今天已经是星期 X，则"下周 X"表示 7 天后。
- "本周"/"这周"= 本周一至本周日...
- "上周"= 本周一往前推 7 天...
- "本周末"= 本周六，若今天已是周六/日，则"本周末"通常指下周六。
- "月底"= 本月最后一天。
- "下个月 X 号"= 下个月第 X 天...
- 用户仅说"X 号"而未说月份时，默认指本月；若该日期已过，则默认下月。
```

值得注意的是这张表在**四个子智能体提示词里完全相同地复用**（行程规划、信息查询、差旅管理、报销），是一张"跨智能体共享决策表"。它不是 Markdown 表格格式（用的是列表），但本质是查找表："输入"= 相对时间表述，"输出"= 换算规则。

类型 4 —— 条件→处理策略分支表

当工具返回的结果需要按严重程度/类型采取不同策略时，分支表上场。差旅冲突分级处理是典型（itinerary-manage-agent-system.md ）：

```text
3. 工具返回 `has_conflict=true` 时，按严重等级处理：
   - **HIGH**（物理上不可能/同日衔接超过24h）：**必须先向用户展示冲突明细并征得明确同意后才能提交**...
   - **MEDIUM**（衔接紧张/路径断裂）：告知用户冲突与建议，让用户选择...
   - **LOW**（同城市重复提交）：一句话提示即可，不需要额外确认。
```

预订的审批检查分支也属此类（booking-agent-system.md L8–10）——条件只有两个值（有/无已审批单），但依然用分支格式写清"有则可订""无则拒绝且说明原因"，不留任何灰地带。

主控提示词里的"情况一/情况二"分法同理（master-agent-system.md L87–117）——按"子智能体返回的内容是完整方案还是追问信息"分两条处理路径，每条下面再给判断标准与操作步骤。
