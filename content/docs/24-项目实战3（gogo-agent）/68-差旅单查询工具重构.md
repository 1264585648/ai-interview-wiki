# ✅差旅单查询工具重构

我们原来在TravelOrderReadTools中定义了一个 query_travel_order方法。

但是后面随着用这个工具的方法越来越多，因为这个方法既查单号又查列表，职责太混乱了。

比如如果我有一个travel_order_id也是用这个方法查，如果我要查询一个用户的所有差旅单也是这个方法，如果要按照日期+状态查询差旅单也是这个方法。

那就导致经常会出现乱七八糟的情况。比如：

我有一个8.12-8.17的出差单，当前状态是已审批。我还有一个8.20-8.22的出差单，当前状态是待审批。这时候，用户要求给8.20的差旅做规划，agent会通过工具去查询APPROVED状态的差旅单，如果今天是19号，那么就会提示已经超期了，无法规划。

主要是因为这个方法承担了太多的职责，所有要查询差旅单的地方都调这一个方法，那我们定义的方法参数就都不能是必填，那么LLM组装参数的时候就可能比较随机。

于是我们做了一次重构。将原来的方法废弃掉。拆分为 query_travel_orders（列表）、query_travel_order（单挑）和 query_travel_order_by_order_id（详情），职责清晰。

```text
@Tool(name = "query_travel_order", description = "查询用户差旅单列表或指定差旅单详情。支持按状态、出发日期范围过滤。")
public String queryTravelOrder(
        AgentSessionContext sessionCtx,
        @ToolParam(name = "origin", description = "出发地城市，如'上海'")
        String origin,
        @ToolParam(name = "destination", description = "目的地城市，如'杭州'")
        String destination,
        @ToolParam(name = "departure_date", description = "出发日期，格式 YYYY-MM-DD")
        String departureDate) {}
```

```text
@Tool(name = "query_travel_order_by_order_id", description = "根据差旅单号，查询指定差旅单详情。")
public String queryTravelOrderByOrderId(
        AgentSessionContext sessionCtx,
        @ToolParam(name = "order_id", description = "差旅单ID") String orderId) {}
```

```text
@Tool(name = "query_travel_orders", description = "查询用户差旅单列表或指定差旅单详情。支持按状态、出发日期范围过滤。")
public String queryTravelOrders(
        AgentSessionContext sessionCtx,
        @ToolParam(name = "status", description = "状态过滤，支持单个或逗号分隔的多个状态，如 DRAFT 或 DRAFT,SUBMITTED。可选值: DRAFT/SUBMITTED/APPROVED/REJECTED/COMPLETED/CANCELLED", required = false) String status,
        @ToolParam(name = "start_date", description = "筛选出发日期不早于此日期的差旅单，格式 YYYY-MM-DD，可选", required = false) String startDate,
        @ToolParam(name = "end_date", description = "筛选出发日期不晚于此日期的差旅单，格式 YYYY-MM-DD，可选", required = false) String endDate) {}
```

这样，只有queryTravelOrders这个方法的参数是选填的，而另外两个方法的参数都是必填，当上下文中有travel_order_id的时候LLM就会调用queryTravelOrderByOrderId、如果上下文中有出发地城市、目的地城市、出发时间的时候他就会调用queryTravelOrder。而如果用户要查询列表，那LLM就会调用queryTravelOrders。

并且我们**修复了一个日期过滤逻辑 bug**：原先 startDate 误用为 departureDate >= startDate，这样会导致只按照出发时间判断，如果我问下周要不要出差时，如果出发时间在本周，Agent会告诉我没有出差。所以我们应该改为时间段重叠判断：departureDate &lt;= endDate AND returnDate >= startDate，修复了日期筛选不准确的问题。

还有就是，这样改造之后，我们在AgentSessionContext中保存的时候，只需要考虑单条精确查询的情况就行了，因为多条查询那种不确定哪条，我们存了也没用。
