# ✅搜索结果自动捕获与持久化

在我们前面讲的形成方案设计工具的实现中，机票、 火车票、酒店等的候选列表是LLM传递给工具的，那么就会带来几个问题：

**幻觉**：LLM 在后续轮次可能“记忆”错误的价格、航班号或政策条款，给出不存在的结果。

**阉割/截断**：工具结果很大时，Agent 只会抽取关键字段放入回复，原始列表、余票、退改规则等被丢弃。（这个问题几乎是必现的）

**上下文压缩后丢失**：AutoContextMemory 在 token 超限时会对历史消息做摘要或卸载，原始搜索结果是最早被压缩的对象之一。

上面的问题一旦发生，就会导致我们的方案设计其实是不完整的。因此需要一套**搜索结果自动捕获与持久化**机制：在工具调用成功后，把原始结果从 ToolResultBlock 里解包、标准化、按业务维度去重，写入 Redis，供后续 reasoning、工具调用或人工复核时直接读取。

整体方案如下：

SearchResultCaptureHook

SearchResultCaptureHook 只关心 PostActingEvent，在工具执行成功后做异步捕获。

```text
@Component
public class SearchResultCaptureHook implements Hook {

    private static final String SHELL_TOOL_NAME = "execute_shell_command";

    private static final String CMD_FLIGHT_SEARCH = "call flight searchLowestPriceFlight";
    private static final String CMD_TRAIN_SEARCH  = "call train searchLowestPriceTrain";
    private static final String CMD_HOTEL_SEARCH  = "call hotel tuniuHotelSearch";

    @Autowired
    private SearchCandidateStore searchCandidateStore;

    @Override
    public int priority() {
        return 21;
    }

    @Override
    @SuppressWarnings("unchecked")
    public <T extends HookEvent> Mono<T> onEvent(T event) {
        if (event instanceof PostActingEvent postActing) {
            return Mono.deferContextual(ctx -> {
                try {
                    handlePostActing(postActing, ctx);
                } catch (Exception e) {
                    // 捕获失败不得影响主流程
                    logger.error("[SearchCapture] 搜索结果捕获异常", e);
                }
                return Mono.just(event);
            }).map(e -> (T) e);
        }
        return Mono.just(event);
    }
}
```

- 全链路 try-catch：捕获异常不抛，避免搜索失败波及主 Agent 流程。
- 仅识别 execute_shell_command：因为当前差旅搜索统一走 tuniu-cli 的 shell 调用。

机票/火车票按 type_departure_arrival_date 组织，酒店按 hotel_city_checkIn_checkOut 组织：

```text
private String buildField(SearchType type, JSONObject args) {
    return switch (type) {
        case FLIGHT, TRAIN -> {
            String dep   = safeStr(args, "departureCityName");
            String arr   = safeStr(args, "arrivalCityName");
            String date  = safeStr(args, "departureDate");
            yield type.name().toLowerCase() + "_" + dep + "_" + arr + "_" + date;
        }
        case HOTEL -> {
            String city     = safeStr(args, "cityName");
            String checkIn  = safeStr(args, "checkInDate", "checkIn");
            String checkOut = safeStr(args, "checkOutDate", "checkOut");
            yield "hotel_" + city + "_" + checkIn + "_" + checkOut;
        }
    };
}
```

同一 field 内，新旧结果按业务主键合并，保留最新版本：

```text
private JSONObject mergeEntries(JSONObject oldEntry, JSONObject newEntry, SearchType type) {
    JSONObject result = new JSONObject(newEntry);

    String listField = listFieldName(type);   // FLIGHT/TRAIN -> "data", HOTEL -> "hotels"
    JSONArray oldList = oldEntry.getJSONObject("data").getJSONArray(listField);
    JSONArray newList = newEntry.getJSONObject("data").getJSONArray(listField);
    JSONArray merged = mergeAndDedup(oldList, newList, type);

    JSONObject mergedData = new JSONObject(newEntry.getJSONObject("data"));
    mergedData.put(listField, merged);
    result.put("data", mergedData);
    return result;
}
```

去重键按业务语义提取：

```text
private String dedupKey(JSONObject item, SearchType type) {
    return switch (type) {
        case FLIGHT -> item.getString("flightNumber") + "|" + item.getString("departureTime");
        case TRAIN  -> item.getString("trainNum")    + "|" + item.getString("departureTime");
        case HOTEL  -> Optional.ofNullable(item.getString("hotelId"))
                               .filter(s -> !s.isBlank())
                               .orElse("name_" + item.getString("hotelName"));
    };
}
```

去重使用 LinkedHashMap，既能去重又保留首次出现的顺序，便于前端按推荐顺序展示。

SearchCandidateStore

```text
@Component
public class SearchCandidateStore {

    private static final String KEY_PREFIX = "planner:search:";
    private static final Duration TTL = Duration.ofHours(24);

    private final StringRedisTemplate redisTemplate;

    public SearchCandidateStore(StringRedisTemplate redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    public static String keyOf(String userId) {
        String uid = (userId == null || userId.trim().isEmpty())
                ? "default"
                : userId.trim().replaceAll("[^a-zA-Z0-9_.-]", "_");
        return KEY_PREFIX + uid;
    }

    public void put(String userId, String field, JSONObject entry) {
        String key = keyOf(userId);
        redisTemplate.opsForHash().put(key, field, entry.toJSONString());
        redisTemplate.expire(key, TTL);
    }

    public String get(String userId, String field) {
        Object value = redisTemplate.opsForHash().get(keyOf(userId), field);
        return value != null ? String.valueOf(value) : null;
    }

    public Map<Object, Object> loadAll(String userId) {
        return redisTemplate.opsForHash().entries(keyOf(userId));
    }

    public void clear(String userId) {
        redisTemplate.delete(keyOf(userId));
    }
}
```

- **Hash 结构**：同一用户的所有搜索候选存在一个 key 下，按 field 区分不同行程维度，便于 HGETALL 一次性加载。
- **24h TTL**：搜索结果属于短期中间态，与机票/酒店库存的时效性匹配。
- **userId 安全过滤**：防止特殊字符注入 Redis key。

ItineraryPlannerTool 从 Redis 读取

规划工具支持 candidates="from_redis"，由 LLM 或上游工具触发。它会调用 SearchCandidateStore.loadAll(userId) 拿到当前用户全部候选，再做笛卡尔积组合、时长/价格归一化、LLM 偏好打分，最后输出 4 个推荐方案：

```text
1. 时间最短
2. 价格最低
3. 最符合偏好
4. 综合最佳
```

最终方案通过 ItineraryPlanStore 单独保存：

```text
@Component
public class ItineraryPlanStore {

    private static final String KEY_PREFIX = "planner:result:";
    private static final Duration RESULT_TTL = Duration.ofHours(24);

    public void save(String userId, String resultJson) {
        String key = keyOf(userId);
        redisTemplate.opsForValue().set(key, resultJson, RESULT_TTL);
    }

    public String load(String userId) {
        String key = keyOf(userId);
        String content = redisTemplate.opsForValue().get(key);
        return content != null && !content.isBlank() ? content : null;
    }
}
```

这样“原始搜索候选”和“规划最终结果”分离：前者用于算法排序与去重，后者用于用户确认、审批单生成、HITL 回显。
