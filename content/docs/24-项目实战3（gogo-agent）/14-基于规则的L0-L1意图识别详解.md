# ✅基于规则的L0/L1意图识别详解

在一个多智能体差旅系统里，每一句用户消息都要先弄清"他想干什么"才能路由到对的子智能体。最可靠的做法当然是让 LLM 理解自然语言后输出意图 JSON——但这要几百毫秒到数秒的推理延迟，且消耗 Token。

然而现实中**超过一半的对话句式高度模板化**：用户说"查一下审批进度"就是在查审批，"帮我报销"就是走报销，这些根本不需要 LLM 来理解——一个正则就够了。如果能在 LLM 之前用纯规则把这些"确定性高、表达模板化"的句子短路掉，就能同时获得三个好处：延迟从秒级降到 50ms 以下（纯内存正则匹配）、省下一次 LLM 调用的 Token 费用、还减少了 LLM 幻觉导致意图误判的概率。

gogo-agent 的做法是在"用户消息进来 → 调度子智能体"之间加了一层**三级编排**（L0 结构启发 → L1 规则 → L2 向量 → L3 LLM 兜底），其中 L1 规则匹配是最核心也最高频命中的一层。本文重点讲 L0/L1。

以下是我们的三层路由识别的入口（IntentRecognitionRouter#route.java）

```text
public Optional<IntentRecognitionResult> route(String question) {
    String normalized = question.trim();

    // -------- L0：多意图结构启发 --------
    if (hasMultiIntentSignal(normalized)) {
        logger.info("[INTENT_ROUTER] L0 检测到并列/顺承连词，疑似多意图复合句，跳过 L1/L2 交给 L3");
        return Optional.empty();
    }

    // -------- L1：规则/关键词匹配 --------
    IntentRuleMatcher.Outcome l1Outcome = ruleMatcher.evaluate(normalized);
    if (l1Outcome.verdict() == IntentRuleMatcher.Verdict.HIT) {
        return Optional.of(l1Outcome.result());          // ★ 短路，省下 L2 + L3
    }
    if (l1Outcome.verdict() == IntentRuleMatcher.Verdict.AMBIGUOUS) {
        return Optional.empty();                          // 子句多类命中跨子智能体：连 L2 也跳过
    }

    // -------- L2 --------
   // -------- L3 --------
}
```

L0和L1的区别

| 层 | 机制 | 兜住的场景 |
| --- | --- | --- |
| L0 | 句中（非句首）出现强连词且句长 ≥10 → 跳过 L1/L2 | 另外半句，**不命中任何规则**的复合句（"订机票，然后把行程发给老板"） |
| L1 | 按标点/连词拆子句独立匹配，命中类别跨 ≥2 个目标子智能体 →`AMBIGUOUS`，连 L2 一起跳过 | 纯标点分隔、无强连词的复合句（"查下机票，帮我报销发票"） |

L0

L0是最外层的"粗筛"：如果句子**同时**满足三个条件就判为多意图，直接跳过 L1/L2：

```text
static boolean hasMultiIntentSignal(String text) {
    if (text == null || text.length() < MULTI_INTENT_MIN_LENGTH) {   // 句长 >= 10
        return false;
    }
    Matcher matcher = MULTI_INTENT_CONJUNCTION.matcher(text); // 命中连词
    return matcher.find() && matcher.start() >= MULTI_INTENT_MIN_CONJUNCTION_OFFSET;  // 连词位置 >= 4
}
```

连词列表现在是**单一维护点**：它定义在 IntentRuleMatcher.STRONG_CONJUNCTIONS（第 70–71 行）里——`"然后|接着|顺便|顺带|以及|并且|另外|同时|完了再|之后再|再帮我|再给我|外加"` 。

句长阈值 10 和位置阈值 4 的作用：短句即使含连词大概率也是单意图（如"顺便问下餐标"），句首连词多为口语衔接词（如"另外你好"）。

设计精髓在于**误判代价极低**——如果 L0 误判了多意图，唯一后果只是走了 L3 慢路径，不会路由到错误的子智能体。

L1

**L1的原则是宁漏判不误判；不确定时直接放行让 L2/L3 处理**。（核心逻辑在IntentRuleMatcher中）

我们在代码中给大家写了个单元测试IntentRuleMatcherTest，专门用来测L1的命中规则的，大家可以运行下这个单测，看看其中的case的命中情况。会更加容易理解。

**数据结构：Rule**

每条规则由三部分组成：

```text
private static final class Rule {
    final IntentCategory category;          // 命中后映射到哪个意图类别
    final Pattern keyword;                  // 正向匹配正则（任一命中即视为候选）
    final List<Pattern> negativeKeywords;   // 排除正则列表（任一命中即排除本规则）

    boolean matches(String text) {
        if (!keyword.matcher(text).find()) {
            return false;
        }
        for (Pattern negative : negativeKeywords) {
            if (negative.matcher(text).find()) {
                return false;                // 被排除词拦截
            }
        }
        return true;                         // 正向命中 + 无排除词 = 规则命中
    }
}
```

**16 条规则（按优先级从高到低）**

规则**硬编码在构造函数中**，注册顺序即优先级。下面逐条列出，把正则里的关键词提炼为人可读的描述：

| # | 意图类别 | 正向关键词（正则，摘要） | 排除词 | 设计意图 |
| --- | --- | --- | --- | --- |
| 1 | GREETING | ^(你好\|您好\|哈喽\|早上好\|…\|在吗\|请问…)+$<br>整句锚定 | 无 | **只有全句都是问候**<br>才命中；"你好，帮我订机票"因为含非问候部分不匹配<br>^...$ |
| 2 | REIMBURSEMENT | 报销\|发票\|贴票\|差旅报销\|费用报销\|提交报销… | 政策/标准/额度/能不能报/怎么报… | 排除"报销政策类"问法，交给 POLICY_QUERY |
| 3 | POLICY_QUERY | 差旅政策\|差标\|超标\|餐标\|住宿标准\|签证\|出差规定… | 无 | 含"标准/政策/规定"的问句归此 |
| 4 | APPROVAL_QUERY | 审批进度\|审批状态\|批了吗\|谁.*审批… | 无 | 关键词已够特异 |
| 5 | TRAVEL_CANCEL | 取消出差\|撤回申请\|不去了\|出差取消… | 无 |  |
| 6 | TRAVEL_MODIFY | 修改.<br>*差旅\|改期\|延期\|把.*<br>日期.*改… | 取消/撤回/撤销 | 排除与"取消"的重叠 |
| 7 | TRAVEL_ORDER_QUERY | 差旅单\|出差记录\|我的差旅\|差旅安排… | 提交/新建/取消/规划/报销/方案… | 排除所有"写"动作和跨类操作 |
| 8 | ATTRACTIONS_QUERY | 景点\|有什么好玩\|打卡\|必去\|美食推荐\|特产… | 无 |  |
| 9 | GENERAL_INFO | 天气\|气温\|限行\|堵不堵\|怎么走\|时差\|汇率… | 机票/航班/火车票/订/预订/报销 | 排除被更具体意图覆盖的表达 |
| 10 | ITINERARY_PLANNING | 规划.<br>*行程\|安排.*<br>行程\|行程方案\|帮我规划… | 无 | **排在 FLIGHT/TRAIN/HOTEL 之前**<br>：当同时包含"规划"+"行程/方案"时优先为规划意图 |
| 11 | FLIGHT_SEARCH | 查机票\|航班\|头等舱\|直飞\|往返机票… | 发票/报销/标准/政策/取消/退票/改签/预订 | 排除"订""退"等动作（交给 BOOKING） |
| 12 | TRAIN_SEARCH | 高铁\|火车票\|动车\|列车\|商务座… | 标准/政策/取消/退票/改签/预订 | 同上 |
| 13 | HOTEL_SEARCH | 查酒店\|住哪里\|大床房\|标间… | 标准/政策/报销/取消/退订/预订 | 同上 |
| 14 | BOOKING | 预订\|下单\|就订这个\|帮我订下\|改签\|退票\|退订… | 无 | 通用兜底，排在具体搜索之后 |
| 15 | TRAVEL_APPLICATION | 申请出差\|我要出差\|帮我提.*申请\|报备出差… | 审批进度/审批状态/取消/查/规划/报销 | 排在最后，避免抢占查询/修改/规划类 |

规则顺序本身编码了消歧语义的核心原则：**"具体动作 > 泛化查询 > 兜底"**——报销/政策/审批/取消/修改这些"一看就知道干什么"的动作词排在前面；搜索类（机票/酒店/火车）紧随其后；预订和新建差旅放最后兜底。这样即使一句话同时包含"机票"和"预订"（如"帮我预订机票"），因为 FLIGHT_SEARCH 会被排除词 "预订" 拦截，BOOKING 就能在更后面接住它。

**核心算法：两步走的 ****evaluate**

这是 L1 最精妙的设计——不是"首中即返"，而是**先做多意图守卫，再做优先级匹配**：

```text
/**
 * 对输入文本执行 L1 规则匹配，返回完整裁决（供 {@link IntentRecognitionRouter} 区分
 * "未命中（可继续 L2）"与"多意图歧义（应连 L2 一起跳过）"）。
 */
public Outcome evaluate(String text) {
    // 空输入无从判定，直接放行给 L2/L3
    if (text == null || text.isBlank()) {
        return Outcome.miss();
    }
    String normalized = text.trim();

    // 步骤 1：多意图守卫——按标点/连词拆成子句，逐句匹配
    List<IntentCategory> clauseCategories = matchClauseCategories(normalized);

    // 如果没有子句命中，则返回 MISS
    if (clauseCategories.isEmpty()) {
        return Outcome.miss();
    }
    // 如果有多个子句命中且命中类别横跨 ≥2 个目标子智能体，则返回 AMBIGUOUS
    long distinctAgents = clauseCategories.stream()
            .map(IntentCategory::getDefaultTargetAgent)
            .distinct()
            .count();
    if (distinctAgents >= 2) {
        return Outcome.ambiguous(clauseCategories);
    }

    // 步骤 2：全文按优先级取首个命中规则
    Rule hit = firstMatch(normalized);
    if (hit == null) {
        return Outcome.miss();
    }
    // 如果有规则命中，则返回 HIT
    return Outcome.hit(IntentRecognitionResult.single(
            IntentRecognitionResult.Source.RULE,
            hit.category,
            IntentRecognitionResult.Confidence.HIGH,
            "L1 规则命中：关键词匹配到「" + hit.category.getDescription() + "」",
            null));
}
```

**步骤 1（子句守卫）**：拆子句独立匹配，判定"是不是多意图"；

**步骤 2（全文首中）**：全文按规则优先级取首个命中，回答"单意图是哪个"。

两步都是"拿规则匹配文本"，但回答的问题不同，需要的匹配语义**刚好相反**：

|  | 步骤 1（子句守卫） | 步骤 2（全文首中） |
| --- | --- | --- |
| 回答的问题 | **是不是**不止一个意图？ | 单意图**是哪个**？ |
| 优化目标 | 高召回（别漏掉第二个意图） | 高精度（别选错意图） |

正常情况下，第一个步骤就能把99%的情况都给识别出来了，但是我实测的过程中，有一个特殊场景会识别错误，如：

```text
修改一下，我的出差申请
```

这个问题在第一个步骤执行时，会被拆分成`修改一下` 、`我的出差申请` 这两个字句，分别去做规则匹配时，第一个字句无法匹配到，第二个子句会匹配到TRAVEL_ORDER_QUERY。最终会返回TRAVEL_ORDER_QUERY，但是实际这句话的意图应该是TRAVEL_MODIFY。

这就是因为我们一上来就把一句话拆分开了，但是实际这句话完整的放到一起的话，是可以通过规则匹配到TRAVEL_MODIFY的。

![](assets/c00f9b6b71f8.png)

**所以，我们需要在步骤一识别到单一意图之后，再做一次完整句子的规则判断，最终确认下实际意图是哪个。**

**三种裁决**

Verdict 枚举定义了三种可能的裁决，配合 Outcome record 一起使用：

```text
public enum Verdict {
    HIT,        // 单类命中：可安全短路，省下 L2 + L3
    AMBIGUOUS,  // 子句多类命中跨子智能体：疑似多意图，连 L2 也跳过直接交 L3
    MISS        // 未命中：交给 L2 继续尝试
}
```
